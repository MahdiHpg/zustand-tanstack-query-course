مدیریت State — چرا، کِی و با چه ابزاری؟

قبل از نصب هر کتابخانه‌ای، باید بدانیم «State» دقیقاً چیست، چند نوع دارد و چرا React به‌تنهایی برای همهٔ آن‌ها کافی نیست. این فصل نقشهٔ کل مسیر دوره است.

در این فصل یاد می‌گیرید

  • State چیست و در یک اپلیکیشن واقعی چند نوع State داریم؟
  • چرا useState و useContext در پروژه‌های بزرگ کافی نیستند؟
  • تفاوت بنیادین Client State و Server State چیست؟
  • چرا ترکیب Zustand و TanStack Query معماری استاندارد امروز است؟

State یعنی چه؟

هر اپلیکیشن React در هر لحظه یک «تصویر از وضعیت» دارد: کاربر کیست؟ سبد خریدش چه چیزی دارد؟ مودالی باز است؟ دادهٔ لیست محصولات هنوز از سرور نیامده؟ به همهٔ این‌ها State (وضعیت) می‌گوییم: داده‌هایی که در طول زمان تغییر می‌کنند و رابط کاربری چیزی است که از این داده‌ها رندر می‌شود.

رابطهٔ معروف React را به یاد بیاورید:

UI = f(state)
رابط کاربری، خروجی یک تابع از State است؛ هر بار State عوض شود، UI دوباره رندر می‌شود.

یعنی کار اصلی ما به‌عنوان توسعه‌دهندهٔ فرانت‌اند، در واقع مدیریت صحیح State است: کجا نگهش داریم؟ چه کسی تغییرش بدهد؟ و از کجا بفهمیم که تغییر کرده؟

اما همهٔ Stateها از یک جنس نیستند

بزرگ‌ترین اشتباه مبتدی‌ها این است که همهٔ داده‌ها را در یک قیف می‌ریزند. یک اپلیکیشن واقعی حداقل چهار نوع State دارد:

نوع Stateمثالویژگی کلیدیابزار مناسب
UI Stateباز/بسته بودن مودال، سایدبار، تم روشن/تاریک، تب فعالکوتاه‌عمر، فقط در همین مرورگر معنا داردuseState / Zustand
Client Data Stateسبد خرید، لیست آهنگ‌های انتخابی، فرم چند مرحله‌ایداده‌ای که «ما» می‌سازیم و مالکش هستیمZustand
Server Stateلیست پست‌ها، پروفایل کاربر، موجودی انبارمالکش سرور است؛ ما فقط نسخهٔ کش‌شدهٔ آن را داریمTanStack Query
URL Stateصفحهٔ فعلی، فیلترها، id محصولباید در آدرس باشد تا لینک‌پذیر و رفرش‌پذیر باشدReact Router
نکتهٔ طلایی

سؤالی که همیشه بپرسید: «مالکِ حقیقی این داده کیست؟» اگر مالک، خودِ مرورگر است (سبد خرید، مودال) → Client State است. اگر مالک، دیتابیسِ سرور است (پست‌ها، موجودی) → Server State است و اگر جایی ذخیره‌اش کنیم فقط یک «کپی محلی و ممکن است کهنه» نگه داشته‌ایم.

چرا useState به‌تنهایی کافی نیست؟

useState عالی است — برای State محلیِ یک کامپوننت. مشکل وقتی شروع می‌شود که چند کامپوننتِ دور از هم به یک State نیاز دارند. رایج‌ترین راه‌حل خام، Prop Drilling است: دادن props از کامپوننت ریشه، لابه‌لای کامپوننت‌هایی که اصلاً به آن نیاز ندارند، تا به مقصد برسد.

src/App.jsx — prop drillingjsx
function App() {
  const [cart, setCart] = useState([])
  return <Layout cart={cart} setCart={setCart} />
}

function Layout({ cart, setCart }) {
  // Layout اصلاً به cart نیاز ندارد؛ فقط جاده است!
  return <Header cart={cart} setCart={setCart} />
}

function Header({ cart, setCart }) {
  // باز هم فقط جاده...
  return <CartBadge cart={cart} setCart={setCart} />
}

function CartBadge({ cart, setCart }) {
  // بالاخره مقصد!
  return <span>{cart.length} قلم</span>
}

در پروژه‌های واقعی این «جاده‌ها» ده‌ها سطح می‌شوند: تغییر کوچک در State یعنی ویرایش پنج فایل و رندر دوبارهٔ کامپوننت‌هایی که ربطی به ماجرا نداشتند.

پس useContext؟ ظاهر فریبنده است

راه‌حل داخلی React، Context است. یک مقدار را بالا تعریف می‌کنیم و هر کامپوننتی هر جای درخت، مستقیم می‌خواند:

src/CartContext.jsxjsx
const CartContext = createContext(null)

function CartProvider({ children }) {
  const [cart, setCart] = useState([])
  const addItem = (item) => setCart((prev) => [...prev, item])
  return (
    <CartContext.Provider value={{ cart, addItem }}>
      {children}
    </CartContext.Provider>
  )
}

// هر جا:
const { cart, addItem } = useContext(CartContext)

برای مقدارهای کم‌تغییر (مثل کاربر لاگین‌شده یا تم) این کافی است. اما سه مشکل جدی دارد:

  • رندر همه‌جانبه: هر تغییری در value باعث رندر دوبارهٔ همهٔ مصرف‌کننده‌های Context می‌شود — حتی آن‌هایی که به آن قسمت تغییرکرده نیاز ندارند. Context هیچ مکانیزم سلکتور ندارد.
  • Provider جهنمی: هر Context یک Provider جداگانه می‌خواهد و درخت کامپوننت‌ها زیر لایه‌لایهٔ Providerها دفن می‌شود.
  • بدون اکشن سازمان‌یافته: منطق تغییر State یا در کامپوننت‌ها پخش می‌شود یا باید در Provider انبار شود؛ در پروژه‌های بزرگ به کد سرگردان تبدیل می‌شود.
هشدار

Context برای مقادیر کم‌تغییر طراحی شده (Theme، Locale، کاربر). اگر داده‌ای مدام تغییر می‌کند (سبد خرید، تایمر، موقعیت موس)، Context شما را به آهسته‌ترین اپ جهان تبدیل می‌کند. برای این کار جای درست، یک استور خارجی مثل Zustand است.

معرفی کوتاه: Zustand

Zustand (واژهٔ آلمانی به معنی «وضعیت») کتابخانه‌ای است که توسط Daishi Kato — یکی از نویسندگان تیم React/Redux — ساخته شد و امروز به محبوب‌ترین گزینهٔ مدیریت Client State تبدیل شده است. سه ویژگی آن را از بقیه جدا می‌کند:

بدون Provider

استور یک هوک ساده است؛ هیچ Context و هیچ Wrapper اضافه‌ای دور App نمی‌پیچد.

حداقل حجم

زیر ۲ کیلوبایت فشرده؛ برای مقایسه Redux Toolkit چندین برابر این است.

سلکتور بومی

کامپوننت فقط به تکه‌ای که می‌خواهد گوش می‌دهد؛ بقیهٔ تغییرات رندر نمی‌کند.

همان سبد خرید، این بار با Zustandjsx
import { create } from 'zustand'

const useCartStore = create((set) => ({
  cart: [],
  addItem: (item) => set((state) => ({ cart: [...state.cart, item] })),
}))

// هر جا — بدون Provider، بدون drilling:
const cart = useCartStore((s) => s.cart)
const addItem = useCartStore((s) => s.addItem)

شاید الان پیچیده به نظر برسد — نگران نباشید؛ از فصل بعد خط‌به‌خط بازش می‌کنیم.

و معرفی کوتاه: TanStack Query

حالا آن سؤال طلایی: «مالکِ لیست پست‌ها کیست؟» سرور. پس در React فقط یک کش (Cache) از آن نگه می‌داریم؛ کپی‌ای که ممکن است کهنه شود و باید رفرش شود. مدیریت این کش — گرفتن، نگه‌داشتن، به‌روزرسانی، دوباره‌گیری بعد از خطا — دقیقاً کار TanStack Query است (که با نام قدیمی React Query هم می‌شناسندش).

بدون آن، همهٔ ما یک الگوی شکننده می‌نویسیم:

الگوی شکنندهٔ «useEffect + fetch»jsx
const [posts, setPosts] = useState([])
const [loading, setLoading] = useState(true)
const [error, setError] = useState(null)

useEffect(() => {
  setLoading(true)
  fetch('/api/posts')
    .then((r) => r.json())
    .then(setPosts)
    .catch(setError)
    .finally(() => setLoading(false))
}, []) // بدون کش، بدون retry، بدون dedup، بدون refresh...

و بعد باید دستی به آن اضافه کنیم: جلوگیری از double-fetch در StrictMode، لغو درخواست هنگام unmount، دوباره‌گیری بعد از برگشتن اینترنت، کش بین تب‌ها، به‌روزرسانی بعد از هر mutation... TanStack Query همهٔ این‌ها را از پیش حل کرده است.

جمع‌بندی فصل

  • State = دادهٔ تغییرپذیری که UI از آن رندر می‌شود؛ UI = f(state).
  • چهار نوع State داریم: UI، Client Data، Server و URL — هرکدام ابزار خودش را می‌خواهد.
  • Prop Drilling و Context در مقیاس بزرگ می‌شکند؛ Context فقط برای مقادیر کم‌تغییر است.
  • Zustand = Client State (سبد خرید، UI). TanStack Query = Server State (هر داده‌ای که مالکش سرور است).

اولین استور: شمارنده

کلاسیک‌ترین شروع. یک فایل جدید بسازید: src/store/useCounterStore.js

src/store/useCounterStore.jsjs
import { create } from 'zustand'

// create یک «هوک» برمی‌گرداند؛ به همین دلیل اسمش را با use شروع می‌کنیم
export const useCounterStore = create((set) => ({
  // ۱) State اولیه
  count: 0,

  // ۲) اکشن‌ها: توابعی که State را تغییر می‌دهند
  increment: () => set((state) => ({ count: state.count + 1 })),
  decrement: () => set((state) => ({ count: state.count - 1 })),
  reset: () => set({ count: 0 }),
}))

سه نکتهٔ بنیادی در همین ۱۰ خط هست:

  • create(callback) یک هوک سفارشی برمی‌گرداند که هر جای برنامه قابل استفاده است — بدون Provider و بدون Context.
  • شیء برگشتیِ callback ترکیبی از داده (اینجا count) و اکشن‌ها (اینجا increment و...) است. در Zustand هیچ اجباری به جداسازی این دو نیست — حتی توصیه هم می‌شود کنار هم بمانند.
  • set مثل setState در React کار می‌کند: اگر یک شیء جزئی بدهید، فقط همان کلیدها با merge به‌روزرسانی می‌شوند و بقیهٔ State دست‌نخورده می‌ماند.

پارامتر get: خواندن آخرین نسخهٔ State داخل اکشن

تا حالا همهٔ اکشن‌ها فقط set را دیسکت می‌کردند. اما create دو پارامتر به شما می‌دهد: (set, get). get همان لحظه، آخرین نسخهٔ State را برمی‌گرداند:

src/store/useWishlistStore.jsjs
import { create } from 'zustand'

export const useWishlistStore = create((set, get) => ({
  items: [],

  // toggle با get: اول بخوان، بعد تصمیم بگیر
  toggle: (product) => {
    const exists = get().items.some((i) => i.id === product.id)
    if (exists) {
      set({ items: get().items.filter((i) => i.id !== product.id) })
    } else {
      set({ items: [...get().items, product] })
    }
  },

  clear: () => set({ items: [] }),
}))

همین کار را می‌شد داخل set((state) => ...) هم کرد؛ تفاوت ظریف اینجاست: اگر اکشن چند set پشت‌سرهم داشته باشد، get() همیشه نسخهٔ تازه را می‌دهد اما پارامتر state داخل یک set فقط نسخهٔ همان لحظه است. در اکشن‌های چندمرحله‌ای (مخصوصاً async) get انتخاب مطمئن‌تری است.

اکشن‌های async: بارگذاری داده با loading و error

اکشن‌ها توابع معمولی هستند؛ پس می‌توانند async باشند. الگوی استاندارد برای فراخوانی API داخل استور:

src/store/useNotificationsStore.jsjs
import { create } from 'zustand'

export const useNotificationsStore = create((set, get) => ({
  items: [],
  status: 'idle', // idle | loading | success | error
  error: null,

  fetchAll: async () => {
    if (get().status === 'loading') return // جلوگیری از درخواست موازی
    set({ status: 'loading', error: null })
    try {
      const res = await fetch('/api/notifications')
      if (!res.ok) throw new Error(`HTTP ${res.status}`)
      const items = await res.json()
      set({ items, status: 'success' })
    } catch (err) {
      set({ status: 'error', error: err.message })
    }
  },

  markAllRead: async () => {
    const ids = get().items.filter((n) => !n.read).map((n) => n.id)
    await fetch('/api/notifications/read', {
      method: 'POST',
      body: JSON.stringify({ ids }),
    })
    set((s) => ({
      items: s.items.map((n) => ({ ...n, read: true })),
    }))
  },
}))

الگوی reset: استخراج State اولیه

با رشد استور، «ریست به اول» سخت می‌شود. راه استاندارد، بیرون کشیدن State اولیه در یک ثابت است:

src/store/useFiltersStore.jsjs
import { create } from 'zustand'

const initialState = {
  query: '',
  category: 'all',
  minPrice: 0,
  sort: 'newest',
}

export const useFiltersStore = create((set) => ({
  ...initialState,
  setQuery: (query) => set({ query }),
  setCategory: (category) => set({ category }),
  setSort: (sort) => set({ sort }),
  reset: () => set({ ...initialState }), // شیء تازه؛ نه replace
}))

دو نکته: اول اینکه reset با merge ساده انجام شد (بدون true)، چون اکشن‌ها جزء State هستند و باید بمانند. دوم اینکه استور فیلترها نمونهٔ خوبی از مرز Client State و URL State است — در پروژهٔ فصل ۱۳ بحثش می‌کنیم.

جمع‌بندی فصل

  • get() آخرین نسخهٔ State را داخل اکشن می‌دهد؛ برای اکشن‌های چندمرحله‌ای و async.
  • set(partial, true) کل State را جایگزین می‌کند — تقریباً هرگز لازم نیست.
  • اکشن async با الگوی idle → loading → success/error نوشته می‌شود؛ اما برای «دادهٔ سرور» جای این الگو TanStack Query است.
  • getState/setState/subscribe استور را به لایه‌های غیر React (interceptor، روتر، توابع کمکی) وصل می‌کنند.
  • ریست استاندارد = استخراج initialState + اکشن reset با merge ساده.

پشت صحنه این اتفاق می‌افتد: کامپوننت در استور subscribe می‌شود. هر بار استور تغییر می‌کند، Zustand سلکتور شما را با State جدید دوباره اجرا می‌کند و نتیجه را با نتیجهٔ قبلی مقایسه می‌کند — با Object.is. اگر برابر باشند، رندری در کار نیست. اگر متفاوت باشند، کامپوننت رندر می‌شود.

پس قانون کارایی Zustand یک جمله است: سلکتور شما باید برای دادهٔ تغییرنکرده، همیشه «همان مقدار» (برابر از نظر Object.is) را برگرداند.

مقادیر اولیه امن‌اند؛ مقادیر مرجعی خطر

سلکتورنوع خروجیهر تغییر استور باعث رندر؟
(s) => s.countعدد/رشته/بولینفقط وقتی خودش عوض شود — امن
(s) => s.user.nameرشتهفقط وقتی name عوض شود — امن
(s) => s.itemsمرجع آرایهفقط وقتی مرجع آرایه عوض شود — امن
(s) => s.items.map(...)آرایهٔ جدیدهمیشه! — باگ رندر
(s) => ({ a: s.a, b: s.b })شیء جدیدهمیشه! — باگ رندر

مقایسهٔ Object.is برای اعداد و رشته‌ها «ارزشی» است، اما برای آرایه و شیء «مرجعی»: هر اجرای s.items.map(...) یک آرایهٔ جدید در حافظه می‌سازد که هرگز با قبلی برابر نیست؛ پس هر تغییر استور (حتی تغییر یک فیلد بی‌ربط) رندر می‌گیرد. بدتر: چون خود State هم هر بار عوض می‌شود، در برخی سناریوها حلقهٔ بی‌نهایت رندر می‌سازد.

راه‌حل ۱: سلکتورهای کوچک و متعدد

به‌جای یک سلکتورِ شیءساز، چند سلکتور مجزا:

بد — شیء جدید در هر رندرjsx

  (s) => ({ name: s.user.name, email: s.user.email })

خوب — دو subscribe مستقلjsx

فراتر از درستی: این شکل هم دقیق‌تر است (فقط تغییر name رندر می‌گیرد، نه تغییر email) هم خواناتر.

راه‌حل ۲: useShallow — مقایسهٔ سطحی

گاهی واقعاً چند فیلد را یک‌جا می‌خواهید (مثلاً در یک map یا بازگشت از یک تابع کمکی). برای این موارد Zustand یک هوک کمکی دارد که خروجی سلکتور را سطحی مقایسه می‌کند: کلیدها و مقادیر اولیهٔ برابر = برابر.

src/store/useCartStore.js و کامپوننتjsx
import { useShallow } from 'zustand/react/shallow'
import { useCartStore } from './useCartStore'

function CartSummary() {
  const { items, coupon } = useCartStore(
    useShallow((s) => ({ items: s.items, coupon: s.coupon }))
  )
  // فقط وقتی مرجعِ items یا مقدار coupon عوض شود رندر می‌گیرد
  return <span>{items.length} قلم — کوپن: {coupon}</span>
}
هشدار — shallow یعنی سطحی، نه عمیق

useShallow فقط یک سطح مقایسه می‌کند. اگر سلکتور هر بار محتوای جدیدی بسازد (مثل s.items.map(i => i.id * 2)) که عناصرش آرایه/شیء تازه‌اند، باز هم هر بار متفاوت است. برای دادهٔ محاسبه‌شدهٔ سنگین، راه‌حل درست useMemo در کامپوننت یا سلکتورِ ذخیره‌شده در استور است.

نکته — تفاوت با نسخهٔ ۴

در نسخهٔ ۴ آرگومان دوم هوک را برابر shallow می‌گذاشتند: useStore(selector, shallow). این API در نسخهٔ ۵ حذف شده و به‌جایش useShallow دور سلکتور پیچیده می‌شود. در مصاحبه‌ها هم می‌پرسند!

محاسبات مشتق‌شده: کجا انجام شود؟

مجموع قیمت سبد از دادهٔ خام مشتق می‌شود. سه جای ممکن:

  • در استور، هنگام هر mutation (نگه‌داشتن total در State): سریع ولی تکرار اطلاعات و ریسک ناهماهنگی — معمولاً نه.
  • در سلکتور: (s) => s.items.reduce(...) — هر اجرا عدد جدیدی «ارزشی» می‌سازد پس رندر مشکل شیء را ندارد؛ اما محاسبه در هر تغییر استور اجرا می‌شود.
  • در کامپوننت با useMemo: فقط وقتی مرجع items عوض شود محاسبه می‌شود — انتخاب پیش‌فرض برای محاسبات سنگین.
src/CartTotal.jsxjsx
import { useMemo } from 'react'
import { useCartStore } from './store/useCartStore'

export default function CartTotal() {
  const items = useCartStore((s) => s.items)

  // فقط وقتی آرایهٔ items عوض شود دوباره حساب می‌شود
  const total = useMemo(
    () => items.reduce((sum, i) => sum + i.price * i.qty, 0),
    [items]
  )

  return <div>جمع کل: {total.toLocaleString('fa-IR')} تومان</div>
}

Transient Updates: بدون رندر با State کار کن

گاهی State تغییری می‌کند که اصلاً نباید UI را رندر کند: موقعیت موس، مقدار اسکرول، تایمر... برای این‌ها subscribe و getState بدون هوک استفاده می‌شود:

src/MousePad.jsx — رندر صفر در هر حرکتjsx
import { useRef, useEffect } from 'react'
import { useMouseStore } from './store/useMouseStore'

export default function MousePad() {
  const ref = useRef(null)

  useEffect(() => {
    // ۱) نوشتن: هر حرکت موس را در استور ذخیره کن — بدون setState در React
    const onMove = (e) => useMouseStore.setState({ x: e.clientX, y: e.clientY })
    window.addEventListener('mousemove', onMove)

    // ۲) خواندن: DOM را مستقیم آپدیت کن، نه با رندر React
    const unsubscribe = useMouseStore.subscribe((s) => {
      if (ref.current) {
        ref.current.style.transform = `translate(${s.x}px, ${s.y}px)`
      }
    })

    return () => {
      window.removeEventListener('mousemove', onMove)
      unsubscribe()
    }
  }, [])

  return <div ref={ref} className="cursor-dot" />
}

Middlewareها — persist، devtools و immer

میان‌افزارها رفتار استور را در چند خط upgrade می‌کنند: ذخیرهٔ دائمی در localStorage، دیباگ زمان‌سفر با Redux DevTools و نوشتن کد قابل جهش با immer.

در این فصل یاد می‌گیرید

  • مفهوم middleware و ترتیب صحیح ترکیب آن‌ها

  • devtools: دیدن اکشن‌ها در Redux DevTools
  • immer: نوشتن State به شکل قابل جهش، امن

Middleware چیست؟

یک middleware (میان‌افزار) تابعی است که دور create پیچیده می‌شود و رفتار استور را تغییر می‌دهد — بدون اینکه منطق شما را عوض کند. حالت کلی:

قالب عمومیjs

می‌توان چند middleware را تو در تو ترکیب کرد. ترتیب توصیه‌شده و رایج (از بیرون به داخل): devtools ← persist ← بقیه (مثل immer):

  )
)

persist — ذخیرهٔ دائمی State

پیش‌فرض Zustand در حافظه است: رفرش صفحه یعنی خداحافظی با سبد خرید. میان‌افزار persist هر تغییر State را در localStorage ذخیره و هنگام اجرا برمی‌گرداند:

src/store/useCartStore.jsjs
import { create } from 'zustand'
import { persist, createJSONStorage } from 'zustand/middleware'

export const useCartStore = create(
  persist(
    (set, get) => ({
      items: [],
      coupon: null,
      _hasHydrated: false,

      addItem: (product) =>
        set((s) => {
          const found = s.items.find((i) => i.id === product.id)
          if (found) {
            return {
              items: s.items.map((i) =>
                i.id === product.id ? { ...i, qty: i.qty + 1 } : i
              ),
            }
          }
          return { items: [...s.items, { ...product, qty: 1 }] }
        }),
      removeItem: (id) => set((s) => ({ items: s.items.filter((i) => i.id !== id) })),
      clearCart: () => set({ items: [], coupon: null }),

      setHasHydrated: (v) => set({ _hasHydrated: v }),
    }),
    {
      name: 'cart-storage',                        // کلید در localStorage (اجباری)
      storage: createJSONStorage(() => localStorage), // پیش‌فرض همین است؛ برای وضوح نوشتیم
      partialize: (state) => ({                    // فقط داده ذخیره شود، نه اکشن‌ها
        items: state.items,
        coupon: state.coupon,
      }),
      onRehydrateStorage: () => (state) => {
        state?.setHasHydrated(true)                // پایان بازیابی
      },
    }
  )
)

چهار آپشن مهم persist:

آپشنکار
nameکلید ذخیره‌سازی (اجباری). یکتا و ثابت نگهش دارید.
storageمحل ذخیره: localStorage، sessionStorage یا هر Storage سازگار. پیش‌فرض localStorage است.
partializeانتخاب بخشی از State برای ذخیره — اکشن‌ها را ذخیره نکنید (بلااستهلاک و بزرگ می‌شوند).
version + migrateکنترل نسخهٔ ساختار ذخیره‌شده و مهاجرت داده‌های قدیمی.
onRehydrateStorageهوک پایان بازیابی — برای ست کردن فلگ hydration یا لاگ.

version و migrate — وقتی شکل داده عوض می‌شود

فرض کنید بعد از انتشار محصول، فیلد qty را به آیتم‌ها اضافه کرده‌اید؛ کاربرانی که نسخهٔ قبلی را در localStorage دارند، دادهٔ بی‌شکل می‌گیرند. راه‌حل:

مهاجرت دادهٔ قدیمیjs
persist(storeApi, {
  name: 'cart-storage',
  version: 2, // نسخهٔ فعلی
  migrate: (persisted, version) => {
    if (version === 1) {
      // نسخهٔ ۱: هر آیتم qty نداشت → برابر ۱ قرار بده
      return {
        ...persisted,
        items: persisted.items.map((i) => ({ ...i, qty: i.qty ?? 1 })),
      }
    }
    return persisted
  },
})

مشکل فلش داده: جلوی رندر «سبد خالی» را بگیرید

بازیابی از localStorage غیرهمزمان است (در v5 با یک میکروتسک). برای یک فریم، State اولیه (سبد خالی) رندر می‌شود و بعد داده می‌آید — کاربر لحظه‌ای «سبد خالی» می‌بیند و اگر بعدش چیزی اضافه کند، ممکن است روی دادهٔ hydrate نشده بنویسد. الگوی حرفه‌ای: فلگ _hasHydrated (که در کد بالا دیدید) و تا true نشده، UI پایدار نشان ندهید:

immer — بنویس ساده، خودش immutable می‌کند

یادتان هست آپدیت تو در تو چه دردسری بود؟ میان‌افزار immer اجازه می‌دهد داخل set مثل کد معمولی «جهش» بنویسید و خودش نسخهٔ immutable می‌سازد:

بدون immerjs
set((s) => ({
  cart: {
    ...s.cart,

    ),
  },

با immerjs
set((s) => {
  const item = s.cart.items.find((i) => i.id === id)
  if (item) item.qty += 1

هشدار

با immer فقط داخل set می‌توانید جهش کنید؛ بیرون از آن State همچنان freeze شده و خواندنش مشکلی ندارد اما تغییرش خطا می‌دهد. ضمناً در set immer دار، چیزی return نکنید — یا جهش کنید یا مقدار برگردانید، نه هر دو.

middleware سفارشی: چطور ساخته می‌شود؟

هر middleware فقط تابعی است که create بعدی را می‌گیرد و نسخهٔ مزین‌شده برمی‌گرداند. یک لاگر ساده بنویسیم تا جعبهٔ جادویی باز شود:

src/store/middleware/logger.jsjs
export const logger = (config) => (set, get, api) =>
  config(
    (args, ...rest) => {
      console.groupCollapsed('action', rest[2] ?? '(unnamed)')
      console.log('prev state:', get())
      set(args, ...rest)
      console.log('next state:', get())
      console.groupEnd()
    },
    get,
    api
  )

یادداشت

میان‌افزارهای دیگری هم در اکوسیستم هست — subscribeWithSelector برای subscribe با سلکتور (فصل ۶)، combine برای ادغام State و اکشن‌های جدا، و بستهٔ zustand-middleware-yjs برای همگام‌سازی چندکاربره. الگو همه یکسان است.

جمع‌بندی فصل

  • middleware تابعی دور create است؛ ترتیب استاندارد: devtools ← persist ← immer.
  • persist با name و بهتر است با partialize؛ برای تغییر ساختار، version + migrate.
  • بازیابی غیرهمزمان است؛ با فلگ hydration از رندرِ «سبد خالی» جلوگیری کنید.
  • devtools اکشن‌ها را در Redux DevTools می‌بیند؛ نام اکشن‌ها را در آرگومان سوم set بدهید.
  • immer جهش امن داخل set می‌دهد؛ یا جهش یا return، نه هر دو.
  • middleware سفارشی = تابعی که config را می‌گیرد و set/get را مزین می‌کند.

TypeScript با Zustand

در Zustand نسخهٔ ۵، فرم استاندارد نوشتن استور تایپ‌دار «کِرید» است — یعنی دو بار پرانتز. دلیلش این است که TypeScript برای اینکه هم State و هم اکشن‌ها را درست حدس بزند، باید تایپ را «قبل از» دیدن تابع شما بداند:

src/store/useCounterStore.tsts
import { create } from 'zustand'

// ۱) تایپ کل State: داده + اکشن‌ها
type CounterState = {
  count: number
  increment: (by?: number) => void
  decrement: (by?: number) => void
  reset: () => void
}

// ۲) create<CounterState>()  ← پرانتز اول؛ بعد تابع
export const useCounterStore = create<CounterState>()((set) => ({
  count: 0,
  increment: (by = 1) => set((s) => ({ count: s.count + by })),
  decrement: (by = 1) => set((s) => ({ count: s.count - by })),
  reset: () => set({ count: 0 }),
}))

از این لحظه اگر increment(2) را با آرگومان رشته صدا بزنید یا فیلدی را تایپ اشتباه بخوانید، کامپایلر خطا می‌دهد — همان چیزی که در تیم‌ها جان شما را نجات می‌دهد.

هشدار — پرانتز جا نماند!

فرم اشتباه: create<CounterState>((set) => ...) (بدون پرانتز وسط). در این شکل استنتاج تایپ اکشن‌ها درست کار نمی‌کند و در مکان‌های استفاده خطای عجیب می‌گیرید. یادتان باشد: create<State>() سپس ((set) => ...).

تایپ‌های کمکی برای persist

وقتی میان‌افزار هم هست، زنجیرهٔ تایپ به ترکیب میان‌افزارها وابسته است؛ برای همین به‌جای نوشتن همه‌چیز دستی، از همان فرم کِرید استفاده می‌کنیم و اگر لازم شد، تایپ State را با Partialize محدود می‌کنیم:

الگوی Slices: استور بزرگ را بشکنید

اگر همهٔ اپ را در یک استور بریزید (کاربر، سبد، فیلترها، نوتیفیکیشن...)، فایل صدها خط می‌شود و هر تغییر، rebase دردناک می‌سازد. الگوی Slices راه‌حل رسمی Zustand است: هر دامنه یک «اسلایس» مستقل، و ترکیب آن‌ها در یک استور واحد. با یک تایپ کمکی شروع می‌کنیم:

src/store/slices/cartSlice.tsts
import { SliceCreator } from '../createStore'

export type CartSlice = {
  items: { id: number; qty: number }[]
  addItem: (id: number) => void
  removeItem: (id: number) => void
  clear: () => void
}

export const createCartSlice: SliceCreator<CartSlice> = (set, get) => ({
  items: [],
  addItem: (id) =>
    set((s) => {
      const found = s.items.find((i) => i.id === id)
      if (found) {
        return { items: s.items.map((i) => (i.id === id ? { ...i, qty: i.qty + 1 } : i)) }
      }
      return { items: [...s.items, { id, qty: 1 }] }
    }),
  removeItem: (id) => set((s) => ({ items: s.items.filter((i) => i.id !== id) })),
  clear: () => set({ items: [] }),
})

subscribeWithSelector: گوش دادن هدفمند

subscribe پیش‌فرض به هر تغییر گوش می‌دهد. میان‌افزار subscribeWithSelector نسخهٔ سلکتوردار می‌دهد — مثل useEffect اما بدون رندر:

subscribe به یک فیلد خاصts
import { subscribeWithSelector } from 'zustand/middleware'

const useBoundStore = create<BoundStore>()(
  subscribeWithSelector((...a) => ({ /* اسلایس‌ها */ }))
)

// هر جا (مثلاً App):
useEffect(() => {
  const unsub = useBoundStore.subscribe(
    (s) => s.items.length,               // فقط این مقدار مهم است
    (len, prevLen) => {                  // فقط وقتی عوض شود صدا می‌شود
      if (len > prevLen) toast('به سبد اضافه شد!')
    },
    { equalityFn: Object.is }            // اختیاری
  )
  return unsub
}, [])

کاربردهای واقعی: نمایش toast بعد از افزودن به سبد، ذخیرهٔ خودکار draft بعد از تغییر متن، گزارش analytics روی اکشن‌های خاص.

۲) استور سبد — قلب پروژه

src/store/useCartStore.jsjs
import { create } from 'zustand'
import { persist } from 'zustand/middleware'
import { COUPONS } from '../data/products'

const initialState = { items: [], couponCode: null, _hasHydrated: false }

export const useCartStore = create(
  persist(
    (set, get) => ({
      ...initialState,

      addItem: (id) =>
        set((s) => {
          const found = s.items.find((i) => i.id === id)
          if (found) {
            return { items: s.items.map((i) => (i.id === id ? { ...i, qty: i.qty + 1 } : i)) }
          }
          return { items: [...s.items, { id, qty: 1 }] }
        }),

      setQty: (id, qty) =>
        set((s) => ({
          items:
            qty <= 0
              ? s.items.filter((i) => i.id !== id)
              : s.items.map((i) => (i.id === id ? { ...i, qty } : i)),
        })),

      removeItem: (id) => set((s) => ({ items: s.items.filter((i) => i.id !== id) })),

      applyCoupon: (code) => {
        const coupon = COUPONS[code.trim().toUpperCase()]
        if (!coupon) return { ok: false, message: 'کد تخفیف نامعتبر است' }
        const subtotal = get().items.reduce((sum, i) => sum + i.qty * priceOf(i.id), 0)
        if (subtotal < coupon.min) {
          return { ok: false, message: 'حداقل مبلغ برای این کد برآورده نشده' }
        }
        set({ couponCode: code.trim().toUpperCase() })
        return { ok: true, message: 'کد تخفیف اعمال شد' }
      },

      removeCoupon: () => set({ couponCode: null }),
      clearCart: () => set({ items: [], couponCode: null }),
      setHasHydrated: (v) => set({ _hasHydrated: v }),
    }),
    {
      name: 'shop-cart',
      partialize: (s) => ({ items: s.items, couponCode: s.couponCode }),
      onRehydrateStorage: () => (state) => state?.setHasHydrated(true),
    }
  )
)

// کمکی: قیمت محصول از کاتالوگ (منبع واحد حقیقت)
import { PRODUCTS } from '../data/products'
const priceOf = (id) => PRODUCTS.find((p) => p.id === id)?.price ?? 0

نقاط آموزشی پروژه

  • دو استور، دو دنیا: useCartStore داده است و useShopUIStore فقط نمایش. کامپوننت گرید محصول از دومی فقط «باز کردن» می‌گیرد؛ از محتوای سبد خبر ندارد.

  • مرجع پایدار برای useMemo: چون items فقط هنگام mutation جدید می‌شود، totals کم محاسبه می‌شود.
  • hydration فلگ: پیام «در حال بازیابی» تا تمام شدن rehydrate رندر می‌شود و بعد لیست واقعی.
هشدار — مرحلهٔ بعدی همان تلهٔ کلاسیک است

TanStack Query و دنیای Server State

چرا دادهٔ سرور با State معمولی فرق دارد؟ در این فصل مرز Client State و Server State را قطعی می‌کنیم، معماری کش TanStack Query را می‌شناسیم و پروژه را آماده می‌کنیم.

در این فصل یاد می‌گیرید

  • پنج ویژگی Server State که آن را از Client State جدا می‌کند
  • نصب و راه‌اندازی QueryClientProvider و تنظیمات پیش‌فرض تیمی
  • نقشهٔ معماری: queryKey، queryFn، کش، observer و garbage collection
  • واژگان کلیدی که تا آخر دوره بارها می‌بینید

چرا نمی‌توان دادهٔ سرور را مثل State معمولی مدیریت کرد؟

سبد خرید مال شماست: فقط شما آن را می‌بینید و فقط شما تغییرش می‌دهید. اما «لیست محصولات» را نه — هر لحظه ممکن است سرور آن را عوض کند، همکار دیگری تغییرش داده باشد و شما اصلاً خبر ندارید. این تفاوتِ ماهوی است، نه فنی. پنج ویژگی Server State:

  1. دور و مشترک: جای ذخیرهٔ اصلی جای دیگری است و ممکن است بدون اطلاع شما تغییر کند.
  2. به‌روزرسانی‌پذیر از بیرون: دیگر کاربران، پنل ادمین، حتی زمان (موجودی و قیمت‌ها).
  3. نیازمند چرخهٔ async: هر دسترسی یعنی شبکه با تأخیر، خطا و تلاش مجدد.
  4. نیازمند حالت‌های فرآیندی: در حال بارگذاری، خطا، موفقیت، stale/fresh — State معمولی این مفاهیم را ندارد.
  5. کِش‌شدنی اما قابل کهنگی: نسخهٔ فعلی فقط یک snapshot است؛ ممکن است کهنه شود.

واژگانی که تا آخر دوره همراه‌ماند

  • Query: خواندن اعلامی از دادهٔ سرور (GET-مانند) با کلید یکتا.
  • Mutation: تغییر دادهٔ سرور (POST/PUT/DELETE) — اعلامی نیست؛ خودتان اجرایش می‌کنید.
  • Invalidation: بعد از mutation، علامت‌گذاری Queryهای مرتبط به stale تا دوباره گرفته شوند — جایگزین دستی sync کردن.
  • Refetch: گرفتن دوبارهٔ داده؛ خودکار (فوکوس/ری‌کانکت/interval) یا دستی.
  • Optimistic Update: قبل از جواب سرور، UI را آپدیت کن؛ اگر شکست، برگرد (فصل ۱۰).

هوکی که جای همهٔ loading/error/useEffectهای دستی می‌نشیند: تعریف query، شناخت وضعیت‌ها، کنترل تازگی با staleTime و تنظیمات عملی retry و cancellation.

اولین useQuery

دو ورودی، همه‌چیز:

  • queryKey: هویت این داده در کش. آرایه است و از چپ به راست «از عمومی به خاص» خوانده می‌شود: ['posts'] لیست پست‌ها، ['posts', 5] پست شمارهٔ ۵، ['posts', { page: 2, q: 'react' } لیست با پارامترها. هر تغییر در محتوای آرایه = یک دادهٔ متفاوت.
  • queryFn: تابعی که Promise داده را برمی‌گرداند. اگر reject شود، Query به status خطا می‌رود و بعد از retryها خطا در error است.
هشدار — queryFn باید واقعاً throw کند

اگر در queryFn خطای HTTP را با if (!res.ok) return null «بلعید»، TanStack Query فکر می‌کند همه‌چیز موفق بوده و UI شما رندر خالی می‌شود. همیشه خطا را پرتاب کنید (همان کاری که getJSON بالا می‌کند).

وضعیت‌ها: status در برابر fetchStatus

مهم‌ترین نکتهٔ مفهومی فصل. هر Query دو چراغ دارد:

چراغمقادیرسؤالی که جواب می‌دهد
status / هوک‌های isPending · isError · isSuccesspending / error / success«آیا اصلاً داده‌ای داریم؟» — دربارهٔ خودِ داده
fetchStatus / isFetchingfetching / idle / paused«همین الان درخواستی در جریان است؟» — دربارهٔ فرآیند شبکه

ترکیب‌های معنادار:

  • isPending && isFetching: بارگذاری اولیه؛ صفحهٔ loading نشان بدهید. (این ترکیب همان isLoading است.)
  • isSuccess && isFetching: دادهٔ قدیمی روی صفحه + رفرش در پس‌زمینه؛ یک ایندیکاتور کوچک نشان دهید، صفحه را خالی نکنید!
  • isSuccess && !isFetching: داده تازه و آرام.
  • isError: خطا — اما دادهٔ قبلی ممکن است هنوز در data باشد.
ممنوع — خالی کردن صفحه هنگام رفرش

if (isFetching) return <Spinner /> یعنی هر برگشت کاربر به تب، کل صفحه به اسپینر تبدیل شود. برای رفرش پس‌زمینه فقط isFetching را به یک نشانگر کوچک وصل کنید؛ isPending مال صفحهٔ loading اولیه است.

رفتار کش در عمل: dedup و refetch

سه کامپوننت مختلف، همان کلید:

سه observer، یک درخواستjsx
// در سه کامپوننت مختلف:
const { data } = useQuery({ queryKey: ['users'], queryFn: api.users })

وقتی داده برمی‌گردد، کش آن را با کلید ['users'] ذخیره می‌کند. بعداً اگر کامپوننت دیگری mount شود، فوراً دادهٔ کش را می‌گیرد (isSuccess از اول) و Query طبق قوانین refetch تصمیم می‌گیرد دوباره بگیرد یا نه. رفرش خودکار سه‌گانه:

  • refetchOnWindowFocus (پیش‌فرض روشن): برگشت به تب اپ → اگر داده stale است، رفرش پس‌زمینه.
  • refetchOnMount (پیش‌فرض روشن): mount دوباره → اگر stale است، رفرش.
  • refetchOnReconnect (پیش‌فرض روشن): برگشتن اینترنت → رفرش.

همهٔ این‌ها با staleTime کنترل می‌شوند: تا داده «تازه» است، هیچ‌کدام اضافه‌کاری نمی‌کنند. تنظیم پیشنهادی تیمی: داده‌های کم‌تغییر (کشورها، لیست دسته‌ها) staleTime بالا (ساعت‌ها)، داده‌های زنده (قیمت، اعلان) staleTime کوتاه یا ۰.

هر بار که کلید عوض شود (مثلاً کاربر سریع بین صفحات می‌زند)، درخواست قبلی به‌طور خودکار بی‌ارزش می‌شود؛ با signal، لغو هم واقعی می‌شود. رقابت پاسخ‌ها (race condition) در TanStack Query اساساً وجود ندارد: هر پاسخ فقط به کلید خودش ثبت می‌شود.

select: تبدیل داده در سطح کش

اگر فقط بخشی از داده لازم دارید (مثلاً نام کاربران از آرایهٔ کامل)، select درست‌کار است — فقط هنگام تغییرِ «خروجی سلکت‌شده» رندر می‌گیرد:

function UserNames() {
  const names = useQuery({
    queryKey: ['users'],
    queryFn: api.users,
    select: (users) => users.map((u) => u.name), // خروجی تبدیل‌شده

  // select در نسخهٔ ۵ به‌صورت داخلی memo می‌شود؛
  // اگر تابع select را بیرون تعریف کردید، با useMemo پایدارش کنید.
  return <ul>{names.data?.map((n) => <li key={n}>{n}</li>)}</ul>
}

هشدار — کلید، فقط دادهٔ پایدار

در queryKey هر چیزی که serialize‌شدنی است می‌گذارید (عدد، رشته، شیء ساده، آرایه). تابع یا کلاس نگذارید. کلیدهای به‌هم‌ریخته یعنی کشِ به‌هم‌ریخته — فصل ۱۱ کل ادبیات کلیدها را ساختار می‌دهد.

دو ابزار آخر این فصل: placeholderData و initialData

  • initialData: دادهٔ اولیهٔ قطعی — Query از همان لحظهٔ اول «success» است (مثلاً دادهٔ SSR یا پیش‌فرض ثابت). فقط وقتی واقعاً از صحتش مطمئنید.
  • placeholderData: دادهٔ «نمایشی» تا fetch واقعی بیاید؛ status می‌ماند pending و isPlaceholderData: true. کاربرد ستاره‌ای‌اش در صفحه‌بندی است (فصل ۱۲): placeholderData: keepPreviousData یعنی «تا دادهٔ صفحهٔ بعد نیامده، صفحهٔ قبل را نشان بده».

جمع‌بندی فصل

  • useQuery({ queryKey, queryFn })؛ کلید = هویت در کش، queryFn = Promise که throw می‌کند.
  • status دربارهٔ داده است (pending/error/success)، fetchStatus دربارهٔ شبکه (fetching/idle).
  • dedup خودکار، refetch خودکار با فوکوس/ری‌کانکت و کنترل با staleTime.
  • signal را به fetch بدهید تا لغو واقعی داشته باشید؛ race condition حذف می‌شود.
  • select برای تبدیل، enabled برای وابستگی، placeholderData و initialData برای تجربهٔ نرم.
تمرین فصل ۹

useMutation — تغییر داده و به‌روزرسانی کش

ساخت، حذف و ویرایش روی سرور؛ چرخهٔ mutation، اینولیدیشن به‌عنوان راهبرد اصلی sync، و به‌روزرسانی خوش‌بینانه با rollback — الگویی که در مصاحبه‌ها پرسیده می‌شود.

در این فصل یاد می‌گیرید

  • تعریف useMutation با mutationFn و فراخوانی با variables
  • چرخهٔ onMutate → onSuccess / onError → onSettled
  • الگوی به‌روزرسانی خوش‌بینانه کامل با snapshot و rollback
  • انتخاب بین invalidation و setQueryData

بر خلاف useQuery که هنگام mount خودش اجرا می‌شود، mutation دستی اجرا می‌شود — وقتی کاربر دکمه را زد:

هشدار — mutate یا mutateAsync؟

mutate() هیچ Promiseای برنمی‌گرداند و خطاها را به onError می‌سپارد — انتخاب پیش‌فرض. اگر منطق بعد از اتمام را «آوانس‌محور» می‌خواهید (مثلاً navigate بعد از موفقیت)، از const res = await mutateAsync(vars) داخل try/catch استفاده کنید. هرگز mutateAsync را بدون try/catch صدا نزنید؛ unhandled rejection می‌گیرید.

چرخهٔ کامل کالبک‌ها

onMutateقبل از درخواست — جای optimistic update
⇐
mutationFnدرخواست شبکه
⇐
onSuccessپاسخ موفق
onErrorخطا (بعد از retryها)
⇐
onSettledدر هر دو حالت — پاک‌سازی

ترتیب اجرا: کالبک‌های خود mutation اول اجرا می‌شوند و بعد کالبک‌های component-level همان فراخوانی (اگر در mutate(vars, { onSuccess }) داده باشید). در تمرین‌های تیمی معمولاً منطق اصلی را در هوک می‌گذاریم و موارد UI-محلی (toast، بستن مودال) را در متد mutate.

invalidation: بعد از تغییر، داده را «کهنه» کن

دو راه برای به‌روز نگه‌داشتن کش بعد از mutation:

  1. Invalidation (پیش‌فرض حرفه‌ای): بگو «دادهٔ X دیگر قابل اعتماد نیست». Queryهای متناظر stale می‌شوند و اگر observer فعال داشته باشند بلافاصله refetch می‌گیرند.
  2. setQueryData دستی: پاسخ سرور را مستقیم در کش بنویس — سریع اما مسئولیت شکل‌دادن به داده با شماست.
دو الگو، پهلو به پهلوjs
// الگوی ۱: invalidation — ساده، همیشه درست
onSuccess: () => {
  queryClient.invalidateQueries({ queryKey: ['posts'] })
}

// الگوی ۲: نوشتن مستقیم پاسخ سرور در کش
onSuccess: (saved) => {
  queryClient.setQueryData(['post', saved.id], saved)
  queryClient.invalidateQueries({ queryKey: ['posts'] }) // لیست همچنان refetch
}

به‌روزرسانی خوش‌بینانه (Optimistic Update)

ایده: تغییر را فوراً در کش بنویس (خوش‌بین باش) تا UI آنی شود؛ اگر سرور جواب خطا داد، به حالت قبل برگرد. الگوی رسمی نسخهٔ ۵:

src/components/PostRow.jsx — حذف خوش‌بینانهjsx
import { useMutation, useQueryClient } from '@tanstack/react-query'
import { api } from '../lib/api'

export default function DeletePostButton({ id }) {
  const queryClient = useQueryClient()

  const removePost = useMutation({
    mutationFn: (id) => api.deletePost(id),

    // ۱) قبل از درخواست: نسخهٔ فعلی را ذخیره کن و کش را آپدیت کن
    onMutate: async (id) => {
      await queryClient.cancelQueries({ queryKey: ['posts'] }) // refetch در جریان را متوقف کن
      const previous = queryClient.getQueryData(['posts'])      // snapshot
      queryClient.setQueryData(['posts'], (old) =>
        old?.filter((p) => p.id !== id) ?? old
      )
      return { previous } // به context کالبک‌های بعدی می‌رسد
    },

    // ۲) خطا: برگرد به snapshot
    onError: (err, id, context) => {
      queryClient.setQueryData(['posts'], context.previous)
      alert('حذف ناموفق بود؛ بازگردانی شد.')
    },

    // ۳) در هر حالت: همیشه با سرور sync کن
    onSettled: () => {
      queryClient.invalidateQueries({ queryKey: ['posts'] })
    },
  })

  return (
    <button disabled={removePost.isPending} onClick={() => removePost.mutate(id)}>
      {removePost.isPending ? '...' : 'حذف'}
    </button>
  )
}

سه گام طلایی که حفظ کنید:

  1. onMutate: cancel + snapshot + setQueryData + برگرداندن { previous }.
  2. onError: بازگردانی از context.previous.
  3. onSettled: invalidation برای همگام‌شدن با حقیقتِ سرور.
هشدار — cancelQueries را حذف نکنید

اگر قبل از setQueryData، یک refetch در جریان باشد، وقتی تمام شود دادهٔ قدیمی را روی تغییر خوش‌بینانه‌تان می‌نویسد و حذفِ آیتم «برمی‌گردد». اول cancel، بعد snapshot، بعد set.

mutationهای هماهنگ با هم: useMutationState

برای نمایش وضعیت‌های جهانی (مثلاً badge «N تغییر در حال ذخیره») لازم نیست وضعیت را جابه‌جا کنید؛ Query خودش همهٔ mutationها را نگه می‌دارد:

جمع‌بندی فصل

  • mutation دستی اجرا می‌شود: useMutation({ mutationFn }) + .mutate(variables).
  • چرخه: onMutate → mutationFn → onSuccess/onError → onSettled.
  • بعد از هر mutation: invalidation (پیش‌فرض) یا setQueryData (پاسخ قطعی).
  • الگوی خوش‌بینانه: cancelQueries + getQueryData/setQueryData + rollback در onError + invalidate در onSettled.
  • useMutationState وضعیت‌های سراسری را بدون state اضافه می‌دهد.

Query Keys و مدیریت کش

کلید، شناسنامهٔ داده در کش است. در این فصل الگوی رسمی Query Key Factory، اینولیدیشن هدفمند با فیلترها، prefetch و ابزارهای دستوری QueryClient را یاد می‌گیرید.

در این فصل یاد می‌گیرید

  • قواعد ساخت کلید و چرا ترتیب عناصر مهم است
  • الگوی Query Key Factory + هوک queryOptions برای تایپ ایمن
  • invalidate با تطبیق جزئی/دقیق و predicate
  • prefetchQuery، ensureQueryData، cancelQueries و بقیهٔ ابزارها

قواعد کلیدنویسی

کلید آرایه است و از چپ به راست، از عمومی به خاص:

سه قاعده:

  • متجانس و سلسله‌مراتبی: هر بخش، پدرِ بخش بعدی است تا تطبیق جزئی (بعداً) معنا داشته باشد.
  • serialize‌پذیر: فقط رشته/عدد/بولین/آرایه/شیء ساده. کلید { page: 2, q: 'react' } با { q: 'react', page: 2 } برابر است (هش پایدار با ترتیب کلیدهای مرتب‌شده).

invalidateQueries و فیلترها

فراخوانیاثر
invalidateQueries({ queryKey: postKeys.all })همهٔ Queryهایی که کلیدشان با ['posts'] شروع می‌شود.

invalidate یعنی: stale کن + اگر observer فعال دارد فوراً refetch، وگرنه فقط برای mount بعدی آمادهٔ refetch باش. به یاد داشته باشید: invalidate هیچ چیز را حذف نمی‌کند؛ دادهٔ قدیمی تا refetch بعدی همان‌جاست.

امکانات پیشرفته — صفحه‌بندی، Infinite و Suspense

صفحه‌بندی نرم با placeholderData، اسکرول بی‌نهایت با useInfiniteQuery، Suspense خالص با useSuspenseQuery، کوئری‌های موازی داینامیک و اتصال به شبکهٔ آفلاین.

در این فصل یاد می‌گیرید

  • صفحه‌بندی بدون فلش با placeholderData: keepPreviousData
  • useInfiniteQuery با initialPageParam و getNextPageParam
  • رندر اعلامی با useSuspenseQuery و ErrorBoundary
  • کوئری‌های داینامیک با useQueries و رفتار آفلاین

صفحه‌بندی با UI ثابت

مشکل کلاسیک صفحه‌بندی: با هر تغییر صفحه، لیست خالی و دوباره پر می‌شود؛ اسکرول می‌پرد و کاربر گیج می‌شود. راه‌حل: تا دادهٔ صفحهٔ جدید نیامده، دادهٔ صفحهٔ قبلی را «نمایشی» نگه دار:

src/components/PaginatedPosts.jsxjsx
import { useState } from 'react'
import { useQuery, keepPreviousData } from '@tanstack/react-query'
import { api } from '../lib/api'
import { postKeys } from '../features/posts/keys'

export default function PaginatedPosts() {
  const [page, setPage] = useState(1)

  const { data, isPlaceholderData, isFetching } = useQuery({
    queryKey: postKeys.list({ page }),
    queryFn: ({ signal }) => api.posts(`?_page=${page}&_limit=10`, signal),
    placeholderData: keepPreviousData, // ← ستارهٔ ماجرا
    staleTime: 30_000,
  })

  return (
    <div style={{ opacity: isPlaceholderData ? 0.6 : 1 }}>
      <ul>{data?.map((p) => <li key={p.id}>{p.title}</li>)}</ul>
      <div>
        <button onClick={() => setPage((p) => p - 1)} disabled={page === 1}>قبلی</button>
        <button onClick={() => setPage((p) => p + 1)}>بعدی</button>
        {isFetching && !isPlaceholderData && <span>در حال آوردن صفحهٔ جدید...</span>}
      </div>
    </div>
  )
}

نکته‌ها: data در حین fetch صفحهٔ بعد، هنوز صفحهٔ قبلی است (isPlaceholderData: true)؛ با opacity کم، حس «در حال تغییر» می‌دهیم بدون خالی‌شدن لیست. هر صفحه وقتی گرفته شد، در کشِ کلید خودش می‌ماند و برگشت به صفحهٔ قبل آنی است.

useInfiniteQuery — اسکرول بی‌نهایت

برای «بارگذاری بیشتر»، ساختار داده فرق می‌کند: پاسخ شامل چند صفحه و نشانگرِ صفحهٔ بعد (cursor) است. سه ورودی اجباری در نسخهٔ ۵:

src/components/InfinitePosts.jsxjsx
import { useInfiniteQuery } from '@tanstack/react-query'
import { api } from '../lib/api'
import { postKeys } from '../features/posts/keys'

export default function InfinitePosts() {
  const { data, isPending, isError, fetchNextPage, hasNextPage, isFetchingNextPage } =
    useInfiniteQuery({
      queryKey: postKeys.lists(), // یا list({ q }) برای فیلترها
      queryFn: ({ signal, pageParam }) => api.posts(`?_limit=10&_page=${pageParam}`, signal),
      initialPageParam: 1,
      getNextPageParam: (lastPage, allPages, lastPageParam) => {
        // JSONPlaceholder: اگر صفحهٔ آخر کمتر از ۱۰ آیتم داشت یعنی تمام
        return lastPage.length < 10 ? undefined : lastPageParam + 1
      },
      maxPages: 5, // حداکثر ۵ صفحه در کش بماند (حافظهٔ موبایل!)
    })

  if (isPending) return <p>بارگذاری...</p>
  if (isError) return <p>خطا!</p>

  // data.pages آرایه‌ای از «پاسخ هر صفحه» است
  const posts = data.pages.flat()

  return (
    <div>
      {posts.map((p) => (
        <article key={p.id}><h4>{p.title}</h4></article>
      ))}
      <button
        onClick={() => fetchNextPage()}
        disabled={!hasNextPage || isFetchingNextPage}
      >
        {isFetchingNextPage
          ? 'در حال بارگذاری...'
          : hasNextPage
            ? 'بارگذاری بیشتر'
            : 'همه را دیدید'}
      </button>
    </div>
  )
}
  • getNextPageParam: از پاسخ آخرین صفحه بگویید صفحهٔ بعد چیست؛ برگرداندن undefined یعنی تمام (hasNextPage: false). اگر API شما cursor در پاسخ می‌دهد (lastPage.nextCursor)، همان را برگردانید.
  • data.pages آرایهٔ صفحات است؛ با data.pageParams هم نشانگرها را دارید.
  • maxPages (جدید در v5) کش صفحات قدیمی را می‌بُرد تا اپ در لیست‌های خیلی بلند از حافظه نترکد.
نکته — اتصال به IntersectionObserver

برای «اسکرول خودکار» به‌جای دکمه، در production با @tanstack/react-virtual یا یک div sentinel و IntersectionObserver ترکیب کنید: if (entry.isIntersecting && hasNextPage) fetchNextPage(). دقت کنید fetchNextPage را در خود کالبک observer صدا می‌زنید، نه در رندر!

useSuspenseQuery — رندر اعلامی

اگر معماری team تان React 18+ و Suspense است، useSuspenseQuery کامپوننت را از تمام ifهای وضعیت خلاص می‌کند: داده همیشه تعریف‌شده است (بدون data?.x) و حالت‌های pending/error به مرزهای Suspense/ErrorBoundary منتقل می‌شوند:

src/components/PostDetailSuspense.jsxjsx
import { Suspense } from 'react'
import { useSuspenseQuery, ErrorBoundary } from '@tanstack/react-query'
import { api } from '../lib/api'
import { postKeys } from '../features/posts/keys'

function PostDetail({ id }) {
  const { data: post } = useSuspenseQuery({
    queryKey: postKeys.detail(id),
    queryFn: ({ signal }) => api.post(id, signal),
  })
  // اینجا data همیشه هست؛ هیچ isPendingی وجود ندارد
  return <h1>{post.title}</h1>
}

export default function Page({ id }) {
  return (
    <ErrorBoundary fallbackRender={({ error }) => <p>خطا: {error.message}</p>}>
      <Suspense fallback={<p>در حال بارگذاری...</p>}>
        <PostDetail id={id} />
      </Suspense>
    </ErrorBoundary>
  )
}
هشدار — کلید باید زیر Suspense باشد

کامپوننتی که useSuspenseQuery دارد باید داخل مرز Suspense رندر شود، وگرنه کل مسیر تا نزدیک‌ترین Suspense بالا معلق می‌شود و کل صفحه لودینگ می‌گیرد. مرزها را دانه‌درشت نه، ولی مرتب بگذارید.

کوئری‌های موازی و داینامیک: useQueries

چند useQuery کنار هم خودبه‌خود موازی اجرا می‌شوند. اما وقتی «تعداد» کوئری‌ها داینامیک است (مثلاً جزئیات N کاربر انتخابی)، تعداد هوک‌ها ثابت نمی‌ماند — قانون هوک‌ها می‌شکند. راه‌حل رسمی:

N کوئری با یک هوکjsx
import { useQueries } from '@tanstack/react-query'
import { api } from '../lib/api'
import { userKeys } from '../features/users/keys'

function UserCards({ userIds }) {
  const results = useQueries({
    queries: userIds.map((id) => ({
      queryKey: userKeys.detail(id),
      queryFn: ({ signal }) => api.user(id, signal),
      staleTime: 5 * 60_000,
    })),
  })

  return (
    <div>
      {results.map((r, i) =>
        r.isPending ? (
          <p key={userIds[i]}>...</p>
        ) : (
          <Card key={userIds[i]} user={r.data} />
        )
      )}
    </div>
  )
}

DevTools حرفه‌ای

افزونهٔ ReactQueryDevtools (که در فصل ۸ نصب کردیم) بیش از نمایش لیست است:

  • وضعیت هر Query (fresh/stale/paused)، زمان آخرین fetch و تعداد observerها را می‌بینید.
  • دکمهٔ invalidate/refetch/reset/copy برای هر Query — دیباگ بدون دست زدن به کد.
  • ساختار درختی کلیدها نشان می‌دهد factory شما درست کار می‌کند یا کلیدها قاطی شده‌اند.
  • در production غیرفعال است؛ فقط dev bundle شامل آن است.

جمع‌بندی فصل

  • صفحه‌بندی نرم = placeholderData: keepPreviousData + کلید پارامتری.
  • Infinite = initialPageParam + getNextPageParam (undefined یعنی تمام) + maxPages.
  • Suspense = useSuspenseQuery داخل مرز Suspense/ErrorBoundary؛ data همیشه هست.
  • کوئری داینامیک = useQueries با آرایهٔ پارامترها.
  • آفلاین با fetchStatus: 'paused' قابل مدیریت است؛ DevTools ابزار روزمرهٔ دیباگ کش است.

src/lib/api.jsjs
import { useAuthStore } from '../stores/useAuthStore'
const BASE = 'https://jsonplaceholder.typicode.com'

async function request(path, { method = 'GET', body } = {}) {
  const headers = { 'Content-Type': 'application/json' }
  // بیرونِ React: خواندن توکن از استور، نه از هوک
  const token = useAuthStore.getState().token
  if (token) headers.Authorization = `Bearer ${token}`

  const res = await fetch(BASE + path, {
    method,
    headers,
    body: body ? JSON.stringify(body) : undefined,
  })
  if (res.status === 401) {
    useAuthStore.getState().clear() // نشست منقضی — یک‌جا و متمرکز
    throw new Error('نشست منقضی شده؛ دوباره وارد شوید')
  }
  if (!res.ok) throw new Error(`API error ${res.status}`)
  return res.status === 204 ? null : res.json()
}

export const api = {
  posts: (params = '', signal) => request(`/posts${params}`, { signal }),
  post: (id, signal) => request(`/posts/${id}`, { signal }),
  addPost: (post) => request('/posts', { method: 'POST', body: post }),
  updatePost: (id, patch) => request(`/posts/${id}`, { method: 'PATCH', body: patch }),
  deletePost: (id) => request(`/posts/${id}`, { method: 'DELETE' }),
  login: async (email) => {
    // JSONPlaceholder لاگین ندارد؛ شبیه‌سازی: کاربر را از /users می‌یابیم
    const users = await request(`/users?email=${encodeURIComponent(email)}`)
    if (!users.length) throw new Error('کاربری با این ایمیل نیست')
    return { user: users[0], token: `demo-token-${users[0].id}` }
  },
}

۳) Mutations در یک فایل

src/features/posts/mutations.jsjs
import { useMutation, useQueryClient } from '@tanstack/react-query'
import { api } from '../../lib/api'
import { postKeys } from './keys'
import { useUIStore } from '../../stores/useUIStore'

export function useAddPost() {
  const qc = useQueryClient()
  const toast = useUIStore((s) => s.toast)

  return useMutation({
    mutationFn: (post) => api.addPost(post),
    onMutate: async (post) => {
      await qc.cancelQueries({ queryKey: postKeys.lists() })
      const previous = qc.getQueryData(postKeys.list({ q: '', page: 1 }))
      qc.setQueryData(postKeys.list({ q: '', page: 1 }), (old) =>
        old ? [{ id: Date.now(), ...post }, ...old] : old
      )
      return { previous }
    },
    onError: (_e, _v, ctx) => {
      qc.setQueryData(postKeys.list({ q: '', page: 1 }), ctx?.previous)
      toast('انتشار ناموفق بود')
    },
    onSuccess: () => toast('پست منتشر شد!'),
    onSettled: () => qc.invalidateQueries({ queryKey: postKeys.all }),
  })
}

export function useDeletePost() {
  const qc = useQueryClient()
  return useMutation({
    mutationFn: (id) => api.deletePost(id),
    onMutate: async (id) => {
      await qc.cancelQueries({ queryKey: postKeys.lists() })
      const previous = qc.getQueryData(postKeys.list({ q: '', page: 1 }))
      qc.setQueryData(postKeys.list({ q: '', page: 1 }), (old) =>
        old?.filter((p) => p.id !== id) ?? old
      )
      return { previous }
    },
    onError: (_e, _v, ctx) =>
      qc.setQueryData(postKeys.list({ q: '', page: 1 }), ctx?.previous),
    onSettled: () => qc.invalidateQueries({ queryKey: postKeys.all }),
  })
}

import { useQuery } from '@tanstack/react-query'
import { postQueries } from '../features/posts/queries'
import { usePostFiltersStore } from '../stores/usePostFiltersStore'
import { PostCard } from './PostCard'

export default function PostList() {

  if (isError) return <p>خطا در دریافت؛ بعداً دوباره تلاش کنید.</p>

  return (
    <section>
      <input
        value={q}
        onChange={(e) => setQ(e.target.value)}
        placeholder="جستجو در عنوان‌ها..."
      />
      <div style={{ opacity: isPlaceholderData ? 0.6 : 1 }}>

import { useState } from 'react'
import { useMutation, useQueryClient } from '@tanstack/react-query'
import { api } from '../lib/api'
import { useAuthStore } from '../stores/useAuthStore'

export default function Header() {
  const user = useAuthStore((s) => s.user)
  const setSession = useAuthStore((s) => s.setSession)
  const clearAuth = useAuthStore((s) => s.clear)
  const qc = useQueryClient()
  const [email, setEmail] = useState('')

  const login = useMutation({
    mutationFn: (mail) => api.login(mail),
    onSuccess: (session) => setSession(session),
  })

  const logout = () => {
    clearAuth()
    qc.clear() // داده‌های سشن‌دار از کش هم بروند
  }

  return user ? (
    <header>
      <span>{user.name}</span>
      <button onClick={logout}>خروج</button>
    </header>
  ) : (
    <header>
      <input value={email} onChange={(e) => setEmail(e.target.value)} placeholder="email" />
      <button disabled={login.isPending} onClick={() => login.mutate(email)}>ورود</button>
    </header>
  )
}

ده سؤال رایج مصاحبه (با پاسخ ۲۰ ثانیه‌ای)

  1. چرا Zustand و نه Context؟ سلکتور بومی و مقایسهٔ مرجع، بدون Provider، با رندر حداقلی؛ Context برای تغییرات پرتعدا طراحی نشده است.
  2. چرا دادهٔ سرور را در Redux/Zustand نمی‌گذاریم؟ چون مالکش سرور است؛ ما فقط کش می‌خواهیم با staleTime و invalidation — دقیقاً کار Query.
  3. staleTime و gcTime چه فرقی دارند؟ اولی «چقدر داده معتبر محسوب می‌شود» و دومی «چقدر بعد از unmount در حافظه بماند».
  4. رفتار refetch خودکار چه وقت‌هاست؟ mount، window focus، reconnect — هر سه شرطی که داده stale باشد.
  5. optimistic update را شرح بده. onMutate: cancel+snapshot+set، onError: rollback، onSettled: invalidate.
  6. queryKey چرا آرایه است؟ برای هش پایدار و تطبیق سلسله‌مراتبی در invalidate.
  7. چرا set تابعی بهتر از set شیءای است؟ برای آپدیت‌های وابسته به State فعلی؛ از stale شدن در آپدیت‌های متوالی جلوگیری می‌کند.
  8. useShallow چه می‌کند؟ مقایسهٔ سطحی خروجی سلکتور تا رندر اضافه نشود؛ جایگزین equalityFn حذف‌شده در v5.
  9. placeholderData و initialData فرقشان؟ اولی نمایشی است و status می‌ماند pending؛ دومی دادهٔ واقعی محسوب می‌شود.
  10. درخواست‌های موازی تکراری چطور ددوپ می‌شوند؟ کلید یکسان → یک درخواست، همهٔ observerها همان داده.

  devtools(

      immer((set, get) => ({
        // State
        count: 0,
        items: [],

        // اکشن sync — تابع آپدیتر
        inc: (by = 1) => set((s) => ({ count: s.count + by })),

        // اکشن با immer (جهش امن)
        addItem: (item) => set((s) => { s.items.push(item) }),

        // اکشن async

          set({ status: 'loading' })
          try {
            const data = await api()
            set({ data, status: 'success' })
          } catch (e) {
            set({ status: 'error', error: e.message })
          }
        },

        // خواندن آخرین State با get
        double: () => set({ count: get().count * 2 }),

        // ریست
        reset: () => set({ count: 0, items: [] }),
      })),
      { name: 'key', partialize: (s) => ({ count: s.count }) }
    )
  )
)
