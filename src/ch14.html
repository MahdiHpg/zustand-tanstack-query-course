تست استور Zustand — بدون React!

زیباترین ویژگی استور خارج از React این است که تستش به رندر نیاز ندارد؛ مستقیم با API استور کار می‌کنید:

src/store/useCartStore.test.jsjs
import { describe, it, expect, beforeEach } from 'vitest'
import { useCartStore } from './useCartStore'

describe('useCartStore', () => {
  beforeEach(() => {
    // State تمیز قبل از هر تست — بدون رندر، بدون Provider
    useCartStore.setState({ items: [], couponCode: null })
  })

  it('آیتم جدید را اضافه می‌کند', () => {
    useCartStore.getState().addItem(1)
    expect(useCartStore.getState().items).toEqual([{ id: 1, qty: 1 }])
  })

  it('افزودن دوباره فقط qty را زیاد می‌کند', () => {
    const { addItem } = useCartStore.getState()
    addItem(1)
    addItem(1)
    expect(useCartStore.getState().items).toEqual([{ id: 1, qty: 2 }])
  })

  it('تعداد صفر یعنی حذف', () => {
    useCartStore.setState({ items: [{ id: 1, qty: 1 }] })
    useCartStore.getState().setQty(1, 0)
    expect(useCartStore.getState().items).toHaveLength(0)
  })

  it('کد نامعتبر را رد می‌کند', () => {
    const result = useCartStore.getState().applyCoupon('NOPE')
    expect(result.ok).toBe(false)
    expect(useCartStore.getState().couponCode).toBeNull()
  })
})
نکته

اگر استور persist دارد، در محیط تست jsdom همان localStorage واقعی است؛ با localStorage.clear() در beforeEach یا ساخت استور با skipHydration در تست‌ها، از نشت بین تست‌ها جلوگیری کنید.

تست کامپوننت‌های Query — کلاینت ایزوله

قانون طلایی: در تست‌ها هرگز از QueryClient اپ استفاده نکنید؛ برای هر تست یک کلاینت تازه بسازید (retry خاموش تا تست‌ها سریع باشند):

src/test/utils.jsx — wrapper مشترکjsx
import { render } from '@testing-library/react'
import { QueryClient, QueryClientProvider } from '@tanstack/react-query'

export function renderWithClient(ui) {
  const queryClient = new QueryClient({
    defaultOptions: {
      queries: { retry: false },
      mutations: { retry: false },
    },
  })
  return render(
    <QueryClientProvider client={queryClient}>{ui}</QueryClientProvider>
  )
}
src/components/PostsList.test.jsxjsx
import { describe, it, expect, vi } from 'vitest'
import { screen, waitFor } from '@testing-library/react'
import { renderWithClient } from '../test/utils'
import { api } from '../lib/api'
import PostsList from './PostsList'

vi.mock('../lib/api', () => ({
  api: { posts: vi.fn() },
}))

describe('PostsList', () => {
  it('لیست پست‌ها را نشان می‌دهد', async () => {
    vi.mocked(api.posts).mockResolvedValue([
      { id: 1, title: 'سلام دنیا' },
      { id: 2, title: 'Zustand چیست' },
    ])
    renderWithClient(<PostsList />)

    expect(screen.getByText(/بارگذاری/)).toBeInTheDocument()
    await waitFor(() => {
      expect(screen.getByText('سلام دنیا')).toBeInTheDocument()
    })
  })

  it('پیام خطا را نشان می‌دهد', async () => {
    vi.mocked(api.posts).mockRejectedValue(new Error('boom'))
    renderWithClient(<PostsList />)
    await waitFor(() => expect(screen.getByText(/خطا/)).toBeInTheDocument())
  })
})

دو الگوی مکمل: به‌جای mock کردن لایهٔ API می‌توانید مستقیم در کش بنویسید (qc.setQueryData(['posts'], fakeData)) تا کامپوننت بدون شبکه تست شود؛ و برای تست خود استورِ Mutation، از useMutationState یا فراخوانی مستقیم mutationFn استفاده کنید.

آنتی‌پترن‌هایی که در code review رد می‌شوند

فهرست ممنوعه

۱) کپی پاسخ سرور در Zustand («دو منبع حقیقت»). ۲) useStore() بدون سلکتور در کامپوننت‌های رندر-سنگین. ۳) ساخت object literal در سلکتور بدون useShallow. ۴) کلید رشته‌ای دست‌ساز به‌جای Factory. ۵) فراخوانی invalidateQueries بدون آرگومان (همه‌چیز را stale می‌کند — گاهی عمدی است، معمولاً تنبلی است). ۶) mutateAsync بدون try/catch. ۷) جهش مستقیم State بدون immer. ۸) fetch داخل useEffect برای دادهٔ سرور — جای آن useQuery است. ۹) نگه‌داشتن فرم‌های بزرگ در استور سراسری (فرم محلی بماند یا با RHF مدیریت شود). ۱۰) persist کردن همهٔ استورها «به‌اعلام حمایت از آینده».

چک‌لیست code review این حوزه

  • هر دادهٔ سرور فقط در کش Query است؛ Zustand فقط client state دارد؟
  • کلیدها با Factory ساخته شده‌اند و پارامترها داخل کلیدند؟
  • staleTime معنادار برای هر دامنه تعریف شده (نه همه صفر، نه همه بی‌نهایت)؟
  • mutationها rollback و onSettled دارند؟ خطا به کاربر نشان داده می‌شود؟
  • خروج کاربر کش را پاک می‌کند؟ توکن‌ها از getState خوانده می‌شوند؟
  • سلکتورها مقدار پایدار برمی‌گردانند؟ Profiler آرام است؟
  • تست استورها و کامپوننت‌های کلیدی پاس است؟

ده سؤال رایج مصاحبه (با پاسخ ۲۰ ثانیه‌ای)

  1. چرا Zustand و نه Context؟ سلکتور بومی و مقایسهٔ مرجع، بدون Provider، با رندر حداقلی؛ Context برای تغییرات پرتعدا طراحی نشده است.
  2. چرا دادهٔ سرور را در Redux/Zustand نمی‌گذاریم؟ چون مالکش سرور است؛ ما فقط کش می‌خواهیم با staleTime و invalidation — دقیقاً کار Query.
  3. staleTime و gcTime چه فرقی دارند؟ اولی «چقدر داده معتبر محسوب می‌شود» و دومی «چقدر بعد از unmount در حافظه بماند».
  4. رفتار refetch خودکار چه وقت‌هاست؟ mount، window focus، reconnect — هر سه شرطی که داده stale باشد.
  5. optimistic update را شرح بده. onMutate: cancel+snapshot+set، onError: rollback، onSettled: invalidate.
  6. queryKey چرا آرایه است؟ برای هش پایدار و تطبیق سلسله‌مراتبی در invalidate.
  7. چرا set تابعی بهتر از set شیءای است؟ برای آپدیت‌های وابسته به State فعلی؛ از stale شدن در آپدیت‌های متوالی جلوگیری می‌کند.
  8. useShallow چه می‌کند؟ مقایسهٔ سطحی خروجی سلکتور تا رندر اضافه نشود؛ جایگزین equalityFn حذف‌شده در v5.
  9. placeholderData و initialData فرقشان؟ اولی نمایشی است و status می‌ماند pending؛ دومی دادهٔ واقعی محسوب می‌شود.
  10. درخواست‌های موازی تکراری چطور ددوپ می‌شوند؟ کلید یکسان → یک درخواست، همهٔ observerها همان داده.

جمع‌بندی فصل

  • تست استور بدون رندر: setState/getState مستقیم + beforeEach تمیز.
  • تست Query با کلاینت ایزوله (retry: false) و mock لایهٔ API یا setQueryData.
  • شش خطای معروف را با علائمشان بشناسید؛ دیاگنوز سریع = اعتماد تیم.
  • فهرست ممنوعه و چک‌لیست review را در پروژه‌تان نصب کنید (ادبیات تیمی).
  • پاسخ‌های ۲۰ ثانیه‌ای مصاحبه را تمرین کنید تا روان بگویید.
