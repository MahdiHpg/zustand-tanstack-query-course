مدیریت State — چرا، کِی و با چه ابزاری؟

قبل از نصب هر کتابخانه‌ای، باید بدانیم «State» دقیقاً چیست، چند نوع دارد و چرا React به‌تنهایی برای همهٔ آن‌ها کافی نیست. این فصل نقشهٔ کل مسیر دوره است.

در این فصل یاد می‌گیرید

  • State چیست و در یک اپلیکیشن واقعی چند نوع State داریم؟
  • چرا useState و useContext در پروژه‌های بزرگ کافی نیستند؟
  • تفاوت بنیادین Client State و Server State چیست؟
  • چرا ترکیب Zustand و TanStack Query معماری استاندارد امروز است؟

State یعنی چه؟

هر اپلیکیشن React در هر لحظه یک «تصویر از وضعیت» دارد: کاربر کیست؟ سبد خریدش چه چیزی دارد؟ مودالی باز است؟ دادهٔ لیست محصولات هنوز از سرور نیامده؟ به همهٔ این‌ها State (وضعیت) می‌گوییم: داده‌هایی که در طول زمان تغییر می‌کنند و رابط کاربری چیزی است که از این داده‌ها رندر می‌شود.

رابطهٔ معروف React را به یاد بیاورید:

UI = f(state)
رابط کاربری، خروجی یک تابع از State است؛ هر بار State عوض شود، UI دوباره رندر می‌شود.

یعنی کار اصلی ما به‌عنوان توسعه‌دهندهٔ فرانت‌اند، در واقع مدیریت صحیح State است: کجا نگهش داریم؟ چه کسی تغییرش بدهد؟ و از کجا بفهمیم که تغییر کرده؟

اما همهٔ Stateها از یک جنس نیستند

بزرگ‌ترین اشتباه مبتدی‌ها این است که همهٔ داده‌ها را در یک قیف می‌ریزند. یک اپلیکیشن واقعی حداقل چهار نوع State دارد:

نوع Stateمثالویژگی کلیدیابزار مناسب
UI Stateباز/بسته بودن مودال، سایدبار، تم روشن/تاریک، تب فعالکوتاه‌عمر، فقط در همین مرورگر معنا داردuseState / Zustand
Client Data Stateسبد خرید، لیست آهنگ‌های انتخابی، فرم چند مرحله‌ایداده‌ای که «ما» می‌سازیم و مالکش هستیمZustand
Server Stateلیست پست‌ها، پروفایل کاربر، موجودی انبارمالکش سرور است؛ ما فقط نسخهٔ کش‌شدهٔ آن را داریمTanStack Query
URL Stateصفحهٔ فعلی، فیلترها، id محصولباید در آدرس باشد تا لینک‌پذیر و رفرش‌پذیر باشدReact Router
نکتهٔ طلایی

سؤالی که همیشه بپرسید: «مالکِ حقیقی این داده کیست؟» اگر مالک، خودِ مرورگر است (سبد خرید، مودال) → Client State است. اگر مالک، دیتابیسِ سرور است (پست‌ها، موجودی) → Server State است و اگر جایی ذخیره‌اش کنیم فقط یک «کپی محلی و ممکن است کهنه» نگه داشته‌ایم.

چرا useState به‌تنهایی کافی نیست؟

useState عالی است — برای State محلیِ یک کامپوننت. مشکل وقتی شروع می‌شود که چند کامپوننتِ دور از هم به یک State نیاز دارند. رایج‌ترین راه‌حل خام، Prop Drilling است: دادن props از کامپوننت ریشه، لابه‌لای کامپوننت‌هایی که اصلاً به آن نیاز ندارند، تا به مقصد برسد.

src/App.jsx — prop drillingjsx
function App() {
  const [cart, setCart] = useState([])
  return <Layout cart={cart} setCart={setCart} />
}

function Layout({ cart, setCart }) {
  // Layout اصلاً به cart نیاز ندارد؛ فقط جاده است!
  return <Header cart={cart} setCart={setCart} />
}

function Header({ cart, setCart }) {
  // باز هم فقط جاده...
  return <CartBadge cart={cart} setCart={setCart} />
}

function CartBadge({ cart, setCart }) {
  // بالاخره مقصد!
  return <span>{cart.length} قلم</span>
}

در پروژه‌های واقعی این «جاده‌ها» ده‌ها سطح می‌شوند: تغییر کوچک در State یعنی ویرایش پنج فایل و رندر دوبارهٔ کامپوننت‌هایی که ربطی به ماجرا نداشتند.

پس useContext؟ ظاهر فریبنده است

راه‌حل داخلی React، Context است. یک مقدار را بالا تعریف می‌کنیم و هر کامپوننتی هر جای درخت، مستقیم می‌خواند:

src/CartContext.jsxjsx
const CartContext = createContext(null)

function CartProvider({ children }) {
  const [cart, setCart] = useState([])
  const addItem = (item) => setCart((prev) => [...prev, item])
  return (
    <CartContext.Provider value={{ cart, addItem }}>
      {children}
    </CartContext.Provider>
  )
}

// هر جا:
const { cart, addItem } = useContext(CartContext)

برای مقدارهای کم‌تغییر (مثل کاربر لاگین‌شده یا تم) این کافی است. اما سه مشکل جدی دارد:

  • رندر همه‌جانبه: هر تغییری در value باعث رندر دوبارهٔ همهٔ مصرف‌کننده‌های Context می‌شود — حتی آن‌هایی که به آن قسمت تغییرکرده نیاز ندارند. Context هیچ مکانیزم سلکتور ندارد.
  • Provider جهنمی: هر Context یک Provider جداگانه می‌خواهد و درخت کامپوننت‌ها زیر لایه‌لایهٔ Providerها دفن می‌شود.
  • بدون اکشن سازمان‌یافته: منطق تغییر State یا در کامپوننت‌ها پخش می‌شود یا باید در Provider انبار شود؛ در پروژه‌های بزرگ به کد سرگردان تبدیل می‌شود.
هشدار

Context برای مقادیر کم‌تغییر طراحی شده (Theme، Locale، کاربر). اگر داده‌ای مدام تغییر می‌کند (سبد خرید، تایمر، موقعیت موس)، Context شما را به آهسته‌ترین اپ جهان تبدیل می‌کند. برای این کار جای درست، یک استور خارجی مثل Zustand است.

معرفی کوتاه: Zustand

Zustand (واژهٔ آلمانی به معنی «وضعیت») کتابخانه‌ای است که توسط Daishi Kato — یکی از نویسندگان تیم React/Redux — ساخته شد و امروز به محبوب‌ترین گزینهٔ مدیریت Client State تبدیل شده است. سه ویژگی آن را از بقیه جدا می‌کند:

بدون Provider

استور یک هوک ساده است؛ هیچ Context و هیچ Wrapper اضافه‌ای دور App نمی‌پیچد.

حداقل حجم

زیر ۲ کیلوبایت فشرده؛ برای مقایسه Redux Toolkit چندین برابر این است.

سلکتور بومی

کامپوننت فقط به تکه‌ای که می‌خواهد گوش می‌دهد؛ بقیهٔ تغییرات رندر نمی‌کند.

همان سبد خرید، این بار با Zustandjsx
import { create } from 'zustand'

const useCartStore = create((set) => ({
  cart: [],
  addItem: (item) => set((state) => ({ cart: [...state.cart, item] })),
}))

// هر جا — بدون Provider، بدون drilling:
const cart = useCartStore((s) => s.cart)
const addItem = useCartStore((s) => s.addItem)

شاید الان پیچیده به نظر برسد — نگران نباشید؛ از فصل بعد خط‌به‌خط بازش می‌کنیم.

و معرفی کوتاه: TanStack Query

حالا آن سؤال طلایی: «مالکِ لیست پست‌ها کیست؟» سرور. پس در React فقط یک کش (Cache) از آن نگه می‌داریم؛ کپی‌ای که ممکن است کهنه شود و باید رفرش شود. مدیریت این کش — گرفتن، نگه‌داشتن، به‌روزرسانی، دوباره‌گیری بعد از خطا — دقیقاً کار TanStack Query است (که با نام قدیمی React Query هم می‌شناسندش).

بدون آن، همهٔ ما یک الگوی شکننده می‌نویسیم:

الگوی شکنندهٔ «useEffect + fetch»jsx
const [posts, setPosts] = useState([])
const [loading, setLoading] = useState(true)
const [error, setError] = useState(null)

useEffect(() => {
  setLoading(true)
  fetch('/api/posts')
    .then((r) => r.json())
    .then(setPosts)
    .catch(setError)
    .finally(() => setLoading(false))
}, []) // بدون کش، بدون retry، بدون dedup، بدون refresh...

و بعد باید دستی به آن اضافه کنیم: جلوگیری از double-fetch در StrictMode، لغو درخواست هنگام unmount، دوباره‌گیری بعد از برگشتن اینترنت، کش بین تب‌ها، به‌روزرسانی بعد از هر mutation... TanStack Query همهٔ این‌ها را از پیش حل کرده است.

معماری نهایی دوره

این تصویر ذهنی را تا آخر دوره حفظ کنید — تقریباً هر تصمیم فنی از روی آن پاس می‌گیرد:

UI (React)کامپوننت‌ها فقط رندر می‌کنند
⇐
Client StateZustand
سبد خرید · UI · فرم
⇐
Server State (کش)TanStack Query
دادهٔ سرور با staleTime و invalidation
⇐
Backend APIREST / GraphQL

قانون سرانگشتی: هر داده‌ای که از API می‌آید به Zustand نمی‌رود — به کشِ Query می‌رود. و هر داده‌ای که فقط در مرورگر معنا دارد، به Query نمی‌رود — به Zustand می‌رود. در فصل ۸ کامل این مرز را یاد می‌گیریم؛ فعلاً همین کافی است.

دربارهٔ کد این کتاب

فصل‌های ۱ تا ۷ با JavaScript می‌نویسیم تا مفهوم‌ها سنگین نشوند؛ از فصل ۶ به بعد (و کل بخش TanStack Query) به TypeScript مهاجرت می‌کنیم — همان‌طور که تیم‌های واقعی کار می‌کنند. کد تایپ‌دار در هر فصل، معادل JS همان الگوست.

جمع‌بندی فصل

  • State = دادهٔ تغییرپذیری که UI از آن رندر می‌شود؛ UI = f(state).
  • چهار نوع State داریم: UI، Client Data، Server و URL — هرکدام ابزار خودش را می‌خواهد.
  • Prop Drilling و Context در مقیاس بزرگ می‌شکند؛ Context فقط برای مقادیر کم‌تغییر است.
  • Zustand = Client State (سبد خرید، UI). TanStack Query = Server State (هر داده‌ای که مالکش سرور است).
  • معماری برنده: UI ← Zustand ← Query Cache ← API.
تمرین فصل ۱ — با کاغذ و قلم!

لیست ۱۰ داده از اپی که هر روز استفاده می‌کنید (مثلاً دیجی‌کالا یا توییتر) بنویسید: سبد خرید، اعلان‌ها، لایک‌ها، تم شبانه و... جلوی هرکدام بنویسید Client State است یا Server State یا URL State و چرا. این تمرین ۱۰ دقیقه‌ای، نیمی از درس فصل ۸ را از قبل در ذهنتان جا می‌اندازد.

در فصل بعد: نصب Zustand و نوشتن اولین استور واقعی — با سه ویژگی که آن را از Context و Redux متمایز می‌کند.
