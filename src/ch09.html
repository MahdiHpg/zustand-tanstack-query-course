useQuery — خواندن داده از سرور

هوکی که جای همهٔ loading/error/useEffectهای دستی می‌نشیند: تعریف query، شناخت وضعیت‌ها، کنترل تازگی با staleTime و تنظیمات عملی retry و cancellation.

در این فصل یاد می‌گیرید

  • نوشتن اولین useQuery با queryKey و queryFn
  • تفکیک status و fetchStatus و رندر بر اساس آن‌ها
  • رفتار کش در عمل: dedup، refetch خودکار و staleTime
  • سلکت‌کردن و تبدیل داده با select، کوئری‌های وابسته با enabled

اولین useQuery

قرارداد پروژه: یک لایهٔ API جدا نگه می‌داریم تا queryFnها فقط «فراخوانی» باشند:

src/lib/api.jsjs
const BASE = 'https://jsonplaceholder.typicode.com'

export async function getJSON(path) {
  const res = await fetch(BASE + path)
  if (!res.ok) throw new Error(`API error ${res.status}`)
  return res.json()
}

export const api = {
  posts: (params = '') => getJSON(`/posts${params}`),
  post: (id) => getJSON(`/posts/${id}`),
  users: () => getJSON('/users'),
}
src/components/PostsList.jsxjsx
import { useQuery } from '@tanstack/react-query'
import { api } from '../lib/api'

export default function PostsList() {
  const { data, isPending, isError, error } = useQuery({
    queryKey: ['posts'],
    queryFn: () => api.posts('?_limit=10'),
  })

  if (isPending) return <p>در حال بارگذاری پست‌ها...</p>
  if (isError) return <p>خطا: {error.message}</p>

  return (
    <ul>
      {data.map((post) => (
        <li key={post.id}>
          <b>{post.id}. {post.title}</b>
        </li>
      ))}
    </ul>
  )
}

دو ورودی، همه‌چیز:

  • queryKey: هویت این داده در کش. آرایه است و از چپ به راست «از عمومی به خاص» خوانده می‌شود: ['posts'] لیست پست‌ها، ['posts', 5] پست شمارهٔ ۵، ['posts', { page: 2, q: 'react' } لیست با پارامترها. هر تغییر در محتوای آرایه = یک دادهٔ متفاوت.
  • queryFn: تابعی که Promise داده را برمی‌گرداند. اگر reject شود، Query به status خطا می‌رود و بعد از retryها خطا در error است.
هشدار — queryFn باید واقعاً throw کند

اگر در queryFn خطای HTTP را با if (!res.ok) return null «بلعید»، TanStack Query فکر می‌کند همه‌چیز موفق بوده و UI شما رندر خالی می‌شود. همیشه خطا را پرتاب کنید (همان کاری که getJSON بالا می‌کند).

وضعیت‌ها: status در برابر fetchStatus

مهم‌ترین نکتهٔ مفهومی فصل. هر Query دو چراغ دارد:

چراغمقادیرسؤالی که جواب می‌دهد
status / هوک‌های isPending · isError · isSuccesspending / error / success«آیا اصلاً داده‌ای داریم؟» — دربارهٔ خودِ داده
fetchStatus / isFetchingfetching / idle / paused«همین الان درخواستی در جریان است؟» — دربارهٔ فرآیند شبکه

ترکیب‌های معنادار:

  • isPending && isFetching: بارگذاری اولیه؛ صفحهٔ loading نشان بدهید. (این ترکیب همان isLoading است.)
  • isSuccess && isFetching: دادهٔ قدیمی روی صفحه + رفرش در پس‌زمینه؛ یک ایندیکاتور کوچک نشان دهید، صفحه را خالی نکنید!
  • isSuccess && !isFetching: داده تازه و آرام.
  • isError: خطا — اما دادهٔ قبلی ممکن است هنوز در data باشد.
ممنوع — خالی کردن صفحه هنگام رفرش

if (isFetching) return <Spinner /> یعنی هر برگشت کاربر به تب، کل صفحه به اسپینر تبدیل شود. برای رفرش پس‌زمینه فقط isFetching را به یک نشانگر کوچک وصل کنید؛ isPending مال صفحهٔ loading اولیه است.

رفتار کش در عمل: dedup و refetch

سه کامپوننت مختلف، همان کلید:

سه observer، یک درخواستjsx
// در سه کامپوننت مختلف:
const { data } = useQuery({ queryKey: ['users'], queryFn: api.users })
// فقط «یک» درخواست شبکه زده می‌شود و هر سه همان data را می‌گیرند.
// به این می‌گویند Request Deduplication.

وقتی داده برمی‌گردد، کش آن را با کلید ['users'] ذخیره می‌کند. بعداً اگر کامپوننت دیگری mount شود، فوراً دادهٔ کش را می‌گیرد (isSuccess از اول) و Query طبق قوانین refetch تصمیم می‌گیرد دوباره بگیرد یا نه. رفرش خودکار سه‌گانه:

  • refetchOnWindowFocus (پیش‌فرض روشن): برگشت به تب اپ → اگر داده stale است، رفرش پس‌زمینه.
  • refetchOnMount (پیش‌فرض روشن): mount دوباره → اگر stale است، رفرش.
  • refetchOnReconnect (پیش‌فرض روشن): برگشتن اینترنت → رفرش.

همهٔ این‌ها با staleTime کنترل می‌شوند: تا داده «تازه» است، هیچ‌کدام اضافه‌کاری نمی‌کنند. تنظیم پیشنهادی تیمی: داده‌های کم‌تغییر (کشورها، لیست دسته‌ها) staleTime بالا (ساعت‌ها)، داده‌های زنده (قیمت، اعلان) staleTime کوتاه یا ۰.

تنظیمات سطح یک Queryjs
const { data: notifications } = useQuery({
  queryKey: ['notifications'],
  queryFn: () => api.get('/notifications'),
  staleTime: 10_000,          // بازنویسیِ پیش‌فرض فقط برای همین Query
  refetchInterval: 30_000,    // polling: هر ۳۰ ثانیه
  refetchIntervalInBackground: false, // در تب پنهان poll نکن
})

retry — تلاش مجدد هوشمند

پیش‌فرض: ۳ بار با تأخیر نمایی (۱ ثانیه، ۲، ۴). کنترل آن:

retry سفارشیjs
useQuery({
  queryKey: ['posts'],
  queryFn: () => api.posts(),
  retry: 2,
  // یا تابعی: خطای ۴۰۴ را نگیر (منبع واقعاً نیست)، بقیه را بگیر
  retry: (failureCount, error) => {
    if (error.message.includes('404')) return false
    return failureCount < 3
  },
  retryDelay: (attempt) => Math.min(1000 * 2 ** attempt, 30_000),
})

لغو درخواست: signal

TanStack Query به هر queryFn یک signal (همان AbortController مرورگر) می‌دهد؛ وقتی Query بی‌observer شود، درخواست لغو می‌شود و شبکه اشغال نمی‌ماند. برای استفاده، signal را به fetch بدهید:

src/lib/api.js — نسخهٔ کاملjs
export const api = {
  posts: (params = '', signal) => getJSON(`/posts${params}`, signal),
  post: (id, signal) => getJSON(`/posts/${id}`, signal),
}

async function getJSON(path, signal) {
  const res = await fetch(BASE + path, { signal })
  if (!res.ok) throw new Error(`API error ${res.status}`)
  return res.json()
}

// در useQuery:
queryFn: ({ signal }) => api.posts('?_limit=10', signal)
نکته

هر بار که کلید عوض شود (مثلاً کاربر سریع بین صفحات می‌زند)، درخواست قبلی به‌طور خودکار بی‌ارزش می‌شود؛ با signal، لغو هم واقعی می‌شود. رقابت پاسخ‌ها (race condition) در TanStack Query اساساً وجود ندارد: هر پاسخ فقط به کلید خودش ثبت می‌شود.

select: تبدیل داده در سطح کش

اگر فقط بخشی از داده لازم دارید (مثلاً نام کاربران از آرایهٔ کامل)، select درست‌کار است — فقط هنگام تغییرِ «خروجی سلکت‌شده» رندر می‌گیرد:

select + memo خودکارjsx
function UserNames() {
  const names = useQuery({
    queryKey: ['users'],
    queryFn: api.users,
    select: (users) => users.map((u) => u.name), // خروجی تبدیل‌شده
  })
  // select در نسخهٔ ۵ به‌صورت داخلی memo می‌شود؛
  // اگر تابع select را بیرون تعریف کردید، با useMemo پایدارش کنید.
  return <ul>{names.data?.map((n) => <li key={n}>{n}</li>)}</ul>
}

کوئری‌های وابسته: enabled

کلاسیک‌ترین سناریو: «اول کاربر را بگیر، بعد پست‌های همان کاربر». تا id کاربر نیامده، کوئری دوم نباید اجرا شود:

src/components/UserPosts.jsxjsx
import { useQuery } from '@tanstack/react-query'
import { api } from '../lib/api'

export default function UserPosts({ email }) {
  // ۱) کاربر از روی ایمیل
  const { data: user } = useQuery({
    queryKey: ['user', email],
    queryFn: ({ signal }) => api.findUserByEmail(email, signal),
  })

  const userId = user?.id

  // ۲) پست‌ها — فقط وقتی userId آماده است
  const postsQuery = useQuery({
    queryKey: ['posts', { userId }],
    queryFn: ({ signal }) => api.posts(`?userId=${userId}`, signal),
    enabled: !!userId, // تا userId نباشد، fetch ممنوع
  })

  if (!user) return <p>در حال پیدا کردن کاربر...</p>
  return <PostList data={postsQuery.data ?? []} />
}
هشدار — کلید، فقط دادهٔ پایدار

در queryKey هر چیزی که serialize‌شدنی است می‌گذارید (عدد، رشته، شیء ساده، آرایه). تابع یا کلاس نگذارید. کلیدهای به‌هم‌ریخته یعنی کشِ به‌هم‌ریخته — فصل ۱۱ کل ادبیات کلیدها را ساختار می‌دهد.

دو ابزار آخر این فصل: placeholderData و initialData

  • initialData: دادهٔ اولیهٔ قطعی — Query از همان لحظهٔ اول «success» است (مثلاً دادهٔ SSR یا پیش‌فرض ثابت). فقط وقتی واقعاً از صحتش مطمئنید.
  • placeholderData: دادهٔ «نمایشی» تا fetch واقعی بیاید؛ status می‌ماند pending و isPlaceholderData: true. کاربرد ستاره‌ای‌اش در صفحه‌بندی است (فصل ۱۲): placeholderData: keepPreviousData یعنی «تا دادهٔ صفحهٔ بعد نیامده، صفحهٔ قبل را نشان بده».

جمع‌بندی فصل

  • useQuery({ queryKey, queryFn })؛ کلید = هویت در کش، queryFn = Promise که throw می‌کند.
  • status دربارهٔ داده است (pending/error/success)، fetchStatus دربارهٔ شبکه (fetching/idle).
  • dedup خودکار، refetch خودکار با فوکوس/ری‌کانکت و کنترل با staleTime.
  • signal را به fetch بدهید تا لغو واقعی داشته باشید؛ race condition حذف می‌شود.
  • select برای تبدیل، enabled برای وابستگی، placeholderData و initialData برای تجربهٔ نرم.
تمرین فصل ۹

کامپوننت PostsList را ارتقا دهید: ۱) سلکتور کاربر، آرایهٔ پست‌ها را بر اساس ورودی جستجو فیلتر کند و با select خروجی فیلترشده بگیرد. ۲) کوئری دوم بسازید که با کلید ['post', id] جزئیات یک پست را بگیرد و با کلیک روی هر پست نمایش دهد (با enabled). ۳) در DevTools ببینید وقتی دو بار روی همان پست کلیک می‌کنید، درخواست جدیدی زده نمی‌شود — چرا؟ (staleTime پیش‌فرض ۶۰ ثانیهٔ App را یادتان هست؟)
