TanStack Query و دنیای Server State

چرا دادهٔ سرور با State معمولی فرق دارد؟ در این فصل مرز Client State و Server State را قطعی می‌کنیم، معماری کش TanStack Query را می‌شناسیم و پروژه را آماده می‌کنیم.

در این فصل یاد می‌گیرید

  • پنج ویژگی Server State که آن را از Client State جدا می‌کند
  • نصب و راه‌اندازی QueryClientProvider و تنظیمات پیش‌فرض تیمی
  • نقشهٔ معماری: queryKey، queryFn، کش، observer و garbage collection
  • واژگان کلیدی که تا آخر دوره بارها می‌بینید

چرا نمی‌توان دادهٔ سرور را مثل State معمولی مدیریت کرد؟

سبد خرید مال شماست: فقط شما آن را می‌بینید و فقط شما تغییرش می‌دهید. اما «لیست محصولات» را نه — هر لحظه ممکن است سرور آن را عوض کند، همکار دیگری تغییرش داده باشد و شما اصلاً خبر ندارید. این تفاوتِ ماهوی است، نه فنی. پنج ویژگی Server State:

  1. دور و مشترک: جای ذخیرهٔ اصلی جای دیگری است و ممکن است بدون اطلاع شما تغییر کند.
  2. به‌روزرسانی‌پذیر از بیرون: دیگر کاربران، پنل ادمین، حتی زمان (موجودی و قیمت‌ها).
  3. نیازمند چرخهٔ async: هر دسترسی یعنی شبکه با تأخیر، خطا و تلاش مجدد.
  4. نیازمند حالت‌های فرآیندی: در حال بارگذاری، خطا، موفقیت، stale/fresh — State معمولی این مفاهیم را ندارد.
  5. کِش‌شدنی اما قابل کهنگی: نسخهٔ فعلی فقط یک snapshot است؛ ممکن است کهنه شود.

هرگز پاسخ سرور را در Zustand کپی نکنید (useUserStore.setState({ profile: data })). از آن لحظه دو نسخه از یک داده دارید و دیر یا زود ناهماهنگ می‌شوند و باگ‌های «گاهی درست است، گاهی نه» می‌سازید. دادهٔ سرور فقط در کش Query زندگی می‌کند.

نصب و راه‌اندازی

terminalbash
npm install @tanstack/react-query
npm install -D @tanstack/react-query-devtools
src/main.jsxjsx
import React from 'react'
import ReactDOM from 'react-dom/client'
import { QueryClient, QueryClientProvider } from '@tanstack/react-query'
import { ReactQueryDevtools } from '@tanstack/react-query-devtools'
import App from './App'

// ۱) یک QueryClient برای کل اپ — بیرون از کامپوننت بسازید
const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 60_000,              // داده تا ۱ دقیقه «تازه» محسوب شود
      retry: 2,                        // دو بار تلاش مجدد قبل از اعلام خطا
      refetchOnWindowFocus: true,      // برگشت به تب = بررسی تازگی
    },
  },
})

ReactDOM.createRoot(document.getElementById('root')).render(
  <React.StrictMode>
    <QueryClientProvider client={queryClient}>
      <App />
      <ReactQueryDevtools initialIsOpen={false} />
    </QueryClientProvider>
  </React.StrictMode>
)

QueryClient مغز متفکر است: کش، پیکربندی و ابزارهای دستوری (invalidate، prefetch و...) همه در آن‌اند و به‌صورت یکتا در کل اپ وجود دارد. QueryClientProvider همان Provider است که در Zustand نداشتیم — اینجا برای اشتراک یک client واحد لازم است.

نکته — تنظیمات پیش‌فرض، جایی که تصمیم‌های تیمی گرفته می‌شود

به‌جای اینکه هر useQuery جداگانه staleTime بدهد، در defaultOptions یک‌بار برای کل اپ تعیین کنید و فقط در موارد استثنا، سطح Query بازنویسی کنید. این همان کاری است که در code review از شما خواسته می‌شود.

هر useQuery یک observer به یک Query در کش اضافه می‌کند. Query با queryKey هویت می‌گیرد (همان کلید دیکشنری). داده‌ای که queryFn برمی‌گرداند در همان Query ذخیره می‌شود. وقتی آخرین observer حذف شود (کامپوننت unmount)، داده تا پایان gcTime (پیش‌فرض ۵ دقیقه) برای استفاده‌های بعدی زنده می‌ماند و بعد از حافظه پاک می‌شود. دو زمان کلیدی:

پارامترپیش‌فرضمعنا
staleTime0چه مدت داده «تازه» است؛ در این مدت هیچ رفرشی به‌صورت خودکار رخ نمی‌دهد (پیش‌فرض ۰ یعنی بلافاصله stale).
gcTime5 دقیقهچند وقت پس از بی‌observer شدن، داده از حافظه پاک شود. (در نسخهٔ ۴ به اسم cacheTime بود.)
هشدار — stale یعنی «ممکن است کهنه باشد»، نه «غیرقابل استفاده»

دادهٔ stale فوراً از کش رندر می‌شود؛ فقط در پس‌زمینه هم fetch تازه اجرا می‌شود و وقتی رسید، UI بی‌دردسر آپدیت می‌شود. الگوی «نمایش فوری کش + به‌روزرسانی در پس‌زمینه» همان چیزی است که اپ‌ها را «سریع» حس می‌کند.

واژگانی که تا آخر دوره همراه‌ماند

  • Query: خواندن اعلامی از دادهٔ سرور (GET-مانند) با کلید یکتا.
  • Mutation: تغییر دادهٔ سرور (POST/PUT/DELETE) — اعلامی نیست؛ خودتان اجرایش می‌کنید.
  • Invalidation: بعد از mutation، علامت‌گذاری Queryهای مرتبط به stale تا دوباره گرفته شوند — جایگزین دستی sync کردن.
  • Refetch: گرفتن دوبارهٔ داده؛ خودکار (فوکوس/ری‌کانکت/interval) یا دستی.
  • Optimistic Update: قبل از جواب سرور، UI را آپدیت کن؛ اگر شکست، برگرد (فصل ۱۰).

پروژهٔ بخش دوم

در ادامهٔ دوره یک API عمومی به اسم JSONPlaceholder را مبنای تمرین می‌کنیم (https://jsonplaceholder.typicode.com) — سرورِ آزمایشی با endpointهای /posts، /users و /comments که همیشه در دسترس است و writeهای ساختگی انجام می‌دهد. برای پروژهٔ فصل ۱۳ همین را به‌عنوان Backend استفاده می‌کنیم؛ در پروژه‌های واقعی فقط آدرس عوض می‌شود.

یادداشت

TanStack Query فریم‌ورک‌محور نیست: هستهٔ آن (@tanstack/query-core) با Vue و Solid و Svelte هم کار می‌کند. هر چیزی که اینجا یاد می‌گیرید، دانش قابل‌حمل است.

جمع‌بندی فصل

  • Server State داده‌ای است که مالکش شما نیست؛ مدیریتش یعنی مدیریت یک کش.
  • معماری: observer (useQuery) → QueryCache → Query (با queryKey) → queryFn → سرور.
  • staleTime = مدت تازگی؛ gcTime = مدت زنده‌ماندن بعد از unmount.
  • تنظیمات پیش‌فرض را یک‌جا در defaultOptions بدهید.
  • دادهٔ سرور هرگز به Zustand کپی نمی‌شود.
تمرین فصل ۸

پروژهٔ Vite بخش اول را با @tanstack/react-query راه‌اندازی کنید: QueryClient با staleTime ۳۰ ثانیه و DevTools. در App یک کامپوننت آزمایشی بسازید که با fetch آدرس https://jsonplaceholder.typicode.com/users را صدا بزند (فعلاً همان useEffect قدیمی — فصل بعد اصلش می‌کنیم) و خروجی را در کنسول چاپ کند. فقط مطمئن شوید اپ بدون خطا بالا می‌آید.
